# 2026-10-08

## 评审 Gemini 给出的 8 条方向性建议（结论：通用清单，非针对本项目）

判定：已实现 3 条（流式点评/演练沙盒/视觉锚点）、已采纳 2 条（记忆错题本=阶段三、
苏格拉底提问=interactions §1.7）、改造后采纳 1 条（eval 阈值触发）、冲突不采纳 2 条
（JSON Mode、评估条）、成本过高不采纳 2 条（走子动画、语音 TTS）。

### 最关键的一处分歧：结构化输出 ≠ 解决幻觉

Gemini 建议「JSON Mode + chess.js 校验 + 自我纠错」，但：
- **JSON Mode 治的是格式错，我们的痛点是内容错**。`===DEMO===` 的 JSON 格式模型一直是对的，
  错的是里面的 SAN 走不通。chess.js 能加载 ≠ 走法合法。
- SDK 实测不支持：`response_format` / `json_object` / `json_schema` 在 `miniprogram.js` 里**均 0 次命中**
  （`strict` 的 126 次是无关代码）。body 虽原样透传，但网关是否支持未验证。
- 自我纠错要多**一次完整往返**（手机网络 3~10s）；候选预生成是**零往返**。
⇒ 它是缓解，D2「走法永不由 LLM 生成」是根治。方向不变。

### 实测数据（有长期价值，别再凭感觉定阈值）

同一局面 `r1bqkb1r/pppp1ppp/2n2n2/4p3/2B1P3/5N2/PPPP1PPP/RNBQK2R w KQkq - 4 4`：

| 深度 | best | cp | 耗时 |
|---|---|---|---|
| 2 | Nc3 | −20 | 1167ms |
| 3 | Nc3 | +40 | 1757ms |
| 4 | Nc3 | −15 | 4347ms |

**仅换深度就漂移 60cp。** 所以任何「Δ > 0.2 = 20cp 判定 blunder」的固定阈值都落在噪声里。

单步 Δ（depth3，起始 best = 40cp，白方视角）：
`Ng5 −125 · Bxf7 −320 · d3 −100 · a3 −165 · Qe2 −75`

**反例**：无害慢手 `a3`（−165）跌幅大于进攻手 `Ng5`（−125）。
⇒ 固定阈值会把 a3 判成比 Ng5 更严重的漏着，棋理上荒谬。
正确做法是「与最佳手的分差」且**固定深度比较**——这正是阶段二 `why_bad` 工具的定义。

另一个要点：起始分就是 best，所以**任何非最佳手 Δ 必为负**，"前后分差"这个指标本身就有系统偏差。

### 我在评审中给出的不同意见（区别于 Gemini）

- **小波动应该是「沉默」，不是「廉价夸赞库」**。棋类教学里"这步正常"没有信息量，
  推送它会稀释信任。阈值应只用于"是否值得打扰用户"，不该用来填充内容。
- depth 4 要 4.3s ⇒ 自动分析只能跑低深度（现有 280ms 防抖 + 低深度是对的）。

### 明确不采纳的两条硬理由（将来别再被说服）

- **走子动画**：Gemini 建议「绝对定位棋子 + CSS transition / WXS / this.animate」。
  但本项目棋盘是 8×8 view 网格 + 文字字形（AGENTS.md §6.1，不用 Canvas），
  改成绝对定位 = **重写棋盘渲染**，与 §6.1–6.3 全部冲突，会破坏 401 项断言里的棋盘回归；
  且预览环境缺 `createSelectorQuery`、WXS 在预览是否可用存疑。收益仅「好看」。
  真要动性能，改 I6（流式 setData ≥120ms 节流）而不是改动画。
- **评估条**：AGENTS.md §3 已明确「优势只显示数值，**不画进度条**」，这是既定产品决策。
  interactions §5.4 也写了「不要用进度条（没有可靠百分比，假进度是撒谎）」。
- **语音 TTS/STT**：免 Key 网关是否提供 TTS **未验证**；同声传译插件需申请且预览环境没有。
  真实价值场景成立（下棋时看文字要切视线），但优先级最低，先列为待验证。

### PGN 是否有采用价值（结论：有，但只在边界）

要劈成两问，答案相反：

**A. 作为「给模型的输出格式」——不采用。**
PGN movetext = SAN + 回合号，与现有 `moves: [...]` 数组等价，换过去幻觉风险不变。
反而更难：要解析 `O-O`/`0-0`、注释 `{...}`、NAG `$1`、变体括号、结果标记；
数组能「在第 k 步精确截断」，半解析的 PGN 字符串做不到。
根因：**我们的工作单元是「从任意局面出发的片段」，不是一整局**——
片段必须带 `[SetUp "1"] [FEN "..."]`，于是 PGN 退化成 "FEN + movetext"，正是已有的东西。

**B. 作为「系统交换格式」——采用，两个位置。**
- **导入（价值最高，且是现成缺口）**：用户从 lichess/chess.com 导出 PGN 贴进来复盘，
  这是**唯一能拿到「用户真实对局」的通道**。现在只支持 FEN，贴整局 PGN 会 `BAD_FEN`。
  ⇒ 阶段三错题本的数据源，缺它就没有数据。必做。
- **导出（成本最低，随时可做）**：现有「复制」按钮加一项「复制为 PGN」即可。
  加分项：点评写进 `{...}` 注释，粘回 lichess 时讲解还在棋谱里。

**内部一律 FEN + UCI，不出现 PGN。** 功能性理由（非偏好）：
阶段三错题去重靠「同一 FEN + 同一错误 UCI」判等；同一局面经不同走子顺序到达时
PGN 不同但 FEN 相同 —— 用 PGN 当主键会把同类错误记成多条，画像就废了。
原则：**PGN 只在进出边界各转换一次。**

**实测（已验证）**：`new Chess(FEN)` 后 `pgn()` 自动输出 SetUp+FEN 头，
`load_pgn()` 载回后 FEN 与原局面逐字节一致，往返无损。
注意 `Game`（utils/game.js）**未暴露** `pgn()/loadPgn()`，需经 `this._chess` 或新增转发。

导入口需 FEN/PGN 自动识别：以 `[` 开头或含 `1.` → PGN，否则 FEN。

**已落档**：以上写进 `docs/agent-plan.md` §4.4「数据格式契约」+ 决策记录 D11；
AGENTS.md §10 的三条跨阶段铁律改为**四条**（新增 FEN+UCI 内部、PGN 仅边界）。
顺手修了决策表 D2/D3 之间多一个空行导致表格被拆成两张的排版缺陷。

### 两条与 Gemini 独立撞车的结论（互相印证，增强信心）

苏格拉底式提问、长期记忆错题本——我们在没有外部输入的情况下已写进文档。
补上我们独有的约束：**提问必须可退让**（用户答不上就立刻切「讲」，Gemini 的"硬引导三次"太刚）、
**主动提及要频控**（同一局最多一次，否则变成翻旧账）。

## 顺手修掉 DemoSession.view() 字段名不一致（既有缺陷）

阶段一没有碰 UI（约定 §3.2），但遗留了一条既有缺陷现在补上：

- 症状：`DemoSession.view()` 返回 `active/canBack/canForward/playing/breadcrumb`，而 `analyze.wxml`
  读 `demoActive/demoCanBack/demoCanForward/demoPlaying/demoBreadcrumb`。`setData(this.demo.view())`
  永远不产出 `demo*` 键，于是这五个页面 data 字段停在 `data()` 默认值（`false`/`''`），
  演示控制条（上一步/下一步/播放/退出）整条 `wx:if="{{demoActive}}"` 永不进入、按钮永不激活。
- 修法：`coach-demo.js view()` 把五个键改名为 `demo*` 前缀，对齐页面 data 约定（页面 data() 本就
  初始化 `demoActive/demoCanBack/...`，属同一套命名）。只改返回对象的键名，不动实例属性
  `this.active` 等（页面 `demoActive()` 方法读的是实例属性，不受影响）。
- 测试：`analyze-page.test.js` 原「缺陷钉」断言旧字段 `active` 存在 → 改为修复验证
  （断言 `demo*` 五个键产出、且 `active` 旧名不再出现）。该套 180→185 项断言。
- 回归：四套全绿，合计 454 项断言。

## 「生成点评」在预览面板显示 "Not found" 的诊断

- 现象：预览面板点「生成点评」显示 `Not found`；用户称上一版在预览能通、当前代码在真机能通。
- 实测核查（本机 curl）：
  - `GET /.cloud/llm/models` 带 `x-wb-webapp-access-key` → **200**，返回完整模型目录；
  - `POST /.cloud/llm/chat/completions`（stream）带同 key → **200**，真实模型输出；
  - 不带/错误 key → **401**（`invalid_client`），不是 404；所以 "Not found" 不是「缺 header/key 失效」。
  - 根路径 `/` → 404，但真实接口路径都 200。**结论：云服务与 `endpoint`/`publishableKey` 完全健康。**
- 代码层核查：`git diff HEAD` 确认 `utils/cloud.js`、`utils/cloud-config.js` 未改；
  `requestCoachComment`/`streamCompletion` 也未改。当前工作树相对 HEAD 的改动（阶段一 Candidate
  Grounding）只让提示词变大、user prompt 多一段 `candidateText`、`MAX_TOKENS` 480→768——
  **不改变请求 URL/头/结构**，体积多 ~1–2KB 不可能触发 404。
- 归因：`Not found` 是 HTTP 404 的 statusText/正文，来自**预览环境网络层**对
  `mp-api.app.workbuddy.host/.cloud/llm/...` 自作主张回的 404（云端实际返回 200）。
  属预览沙箱出网限制，不是本项目代码或配置问题；真机/微信开发者工具能通印证这一点。
- 处理：把难懂的 "Not found" 换成可读文案。`utils/ai-client.js#llmErrorInfo` 新增 `status===404`
  分支 → 归类为 `notfound`，文案说明「预览环境网络层无法访问该服务、端上引擎分析不受影响、
  请在微信开发者工具或真机重试」，并把 `HTTP 404` 带进 `detail` 便于「运行日志」排查；
  `shouldTryNextModel` 对 404 返回 false（换模型救不了）。`analyze-page.test.js` 补 3 条 404 断言。
- 回归：四套全绿（engine 153 / adapter 68 / page 188 / tools 48）。
- 给用户的操作建议：预览里看不到云端点评属环境限制；要验证点评功能请用**微信开发者工具**或**真机**
  （记得把 `https://mp-api.app.workbuddy.host` 加进 request 合法域名，见 AGENTS.md §10.3 #12）；
  端上三条路线分析在任何环境都可用。
