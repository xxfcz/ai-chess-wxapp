### 踩坑（可复用）
1. `chess.js@0.10.3` 的 `validate_fen()` **只校验不载入**，必须显式 `load(fen)`，否则棋盘永远是初始局面。

   若先把实例存进局部变量，翻转后就操作到旧实例上了（自由模拟走子永远失败）。
4. 「自由模拟双方」的合法落点必须在**副本**上翻转行棋方再算（`legalTargetsFrom`/`buildProbe`），
   否则拖动对方棋子时高亮为空、永远走不动。
5. 分析进行中点击「生成点评」曾误报「请先完成局面分析」；改成
   `runAnalyze()` 返回可 await 的 Promise + `ensureAnalysis(fen)` 轮询兜底。

## 追加修复：`wx.createSelectorQuery is not a function`

**现象**：右侧预览一打开就报错，页面白/不可用。

**根因**：WorkBuddy 的网页版预览运行时只实现了微信接口的一个子集，
**不提供 `wx.createSelectorQuery`**。原来棋盘用 `<canvas type="2d">` + `createSelectorQuery().select('#chessboard')`
拿节点，取不到就抛错，整个页面初始化中断。

**改法**：整块换掉 Canvas 方案。
- 删除 `utils/board-render.js`（Canvas 绘制层）。
- 新增 `utils/board-model.js`：纯函数，把棋局状态编译成 64 个格子的视图数据
  `{ sq, cls, glyph, color, mark, ct, cb }`，棋盘由 WXML 的 8×8 `view` 网格渲染，
  棋子是格内文字字形（实心 ♔♕♖♗♘♙，靠 `.piece-w/.piece-b` 颜色区分黑白）。
- 新增 `utils/device.js`：窗口宽度与 Toast 的安全取值，`getWindowInfo → getSystemInfoSync →
  window.innerWidth → documentElement.clientWidth → 375` 逐级降级，全部 try/catch，永不抛错。
- 拖拽落点不再需要棋盘坐标：记下按下格与手指起点，用 `位移 ÷ 格宽` 四舍五入得到行列偏移。
- `utils/geometry.js` 补了 `squareToCell/cellToSquare/isLightSquare`，纯函数无 wx 依赖。

**顺带修掉一个隐藏更深的 bug**：`board-model.js` 从 chess.js 的 `board()` 取子时写成了 `board[rank]`，
但 `board()` 第 0 行是**第 8 横线**，应为 `board[7 - rank]`。结果是**整盘上下镜像 + 黑白互换**——
起始局面因为对称完全看不出来，任何非对称局面（比如没走几步的中局）都会画错。
已改为 `board[7 - rank]`，并在 `analyze-page.test.js` 里加了 5 条回归断言
（g2 黑王、e1 白王、h1 白车各自落对格，且镜像位置 g7/e8/h8 必须为空）。

**验证**：两套用例全绿；项目代码里 `wx.` 的调用只剩 `getWindowInfo / getSystemInfoSync / showToast`，
全部包在 `device.js` 的降级逻辑里；SDK 侧也只用到 `getAccountInfoSync / getStorageSync / login / request`，
同样不含 `createSelectorQuery`。

**预览环境的两条已知限制（记住免得再踩）**：
1. 不实现 `wx.createSelectorQuery`（本页事故根因）。
2. 触摸拖拽类事件在预览里可能退化成鼠标事件 —— 所以交互**必须同时提供 `bindtap` 点选路径**，
   现在的页面点一下棋子、再点一下目标格也能走子，不依赖拖拽。

## 追加修复二：三条路线渲染不出来 + 点评误报「模型服务暂时不可用」

**现象 A**：点「AI 分析」，只显示「点击任一路线…」+「深度 3 · 15084 节点 · 249ms」，**三条路线一行都没有**。

**原因**：`analyze.wxml` 里路线循环把循环变量写进了 **`wx:for` 元素自身的属性**：
```html
<view wx:for="{{analysisLines}}" wx:key="rank"
      class="line {{hintIndex === index ? 'line-active' : ''}}"
      data-index="{{index}}" bindtap="onPreviewLine">
```
预览环境在渲染元素**自身**属性时拿不到 `index`，整行渲染不出来；
而同级说明文字（不依赖 `index`）照常显示 —— 完美对上现象。
对照：棋盘 `wx:for="{{cells}}"` 的属性只引用 `item.*`，所以一直正常；`moveRows` 也不引用 `index`。
也就是说**全页只有路线循环引用了 `index`，也只有它渲染失败**。

**改法（约定：模板里不要在循环元素自身的属性中引用循环变量）**
- 下标与高亮态随数据下发：`pages/analyze/analyze.js#buildLineViews()` 给每条路线补
  `idx`（0 基下标）、`key`（字符串唯一键）、`active`（是否高亮）；
- 模板改成 `class="line {{item.active ? 'line-active' : ''}}" data-index="{{item.idx}}"`
  与 `wx:key="key"`；
- 点击高亮改由 `applyLineActive(index)` 重建数组（不用 setData 路径语法，兼容性更好）；
- `moveRows` 的 `wx:key="no"`（数字）也换成字符串键 `key`，一并消除数字键风险；
- 顺手去掉模板里的 `<block>`（预览环境支持范围未知），改成独立 `wx:if`。

**现象 B**：点「生成点评」报「模型服务暂时不可用，请稍后再试。」，但云服务其实完全正常。

**原因有两层**：
1. **误报**：SDK 在底层请求失败时统一抛 `code` 以 `gateway_` 开头的错误
   （`gateway_network_error` / `gateway_stream_interrupted` / `gateway_invalid_response`），
   其中 `gateway_network_error` 就是「wx.request 失败/中断」。原来的 `describeLLMError()`
   把整个 `gateway_*` 都翻成「模型服务暂时不可用」→ 把环境限制误报成云端故障。
2. **真实故障**：预览环境的 `wx.request` **接受 `enableChunked: true`，但返回的任务对象上没有
   `onChunkReceived`**。SDK 的流式实现是无条件调用 `task.onChunkReceived(...)` 的，
   于是同步抛 `TypeError: task.onChunkReceived is not a function`，被包成 `gateway_network_error`。
   （另外注意：该 SDK **只支持流式**，`create({stream:false})` 会抛 `request_stream_required`，
   所以不能靠「退回非流式」来解决，只能自己补分块能力。）

**改法**
- `utils/workbuddy-cloud-diagnostics.js`：wx 适配器新增**自适应分块降级**。
  先按原生分块发起；若返回的任务没有 `onChunkReceived`，中止它，改用一次性普通请求
  （`responseType: 'text'`），把**整包响应体当成单个分片**用自写的 `encodeUtf8()` 编成
  `ArrayBuffer` 推给 SDK 的 SSE 解析器。结论记进模块级 `chunkedSupported`，之后不再白发探测请求。
  另外补了分片/响应头缓冲（回调可能早于监听器注册）、两段看门狗超时（45s/50s）、
  存储接口的防御性透传（环境缺 API 时返回 '' 而不是抛错）。
  适配器暴露 `streamingStatus()`（null=未探测 / true=原生支持 / false=已降级）供自检。
- `utils/ai-client.js`：`describeLLMError()` 拆成 `llmErrorInfo(err)` →
  `{ message, detail, kind }`；`gateway_network_error` 改报网络受限并说明端上分析不受影响，
  只有真的 `gateway_*`（非网络类）与 `model_*` 才报「模型服务暂时不可用」。
  `detail` 汇总错误码 + 逐层 `cause.message`，界面用小字等宽行显示，便于定位。
- `pages/analyze/analyze.js/.wxml`：新增 `coachDetail`（排查线索行）与 `commentingHint`
  （降级环境下要等完整结果，提示 10~30 秒）。

**实网验证**（`.workbuddy/tests/cloud-live-probe.js`，需网络、耗少量额度）：
用**真实云服务** + 一个「像预览一样不给分块回调」的 wx 实现跑完整链路 ——
30 个模型、流式点评拿到 **192 个分片 / 约 24s** 的真实中文点评、`streamingStatus() === false`。
证明「不支持分块流式的环境」经适配后功能可用（只是失去逐字增量渲染，一次性显示）。

**测试**：新增 `.workbuddy/tests/cloud-adapter.test.js`（8 节，含原生透传、降级、结论复用、
同步回调不丢分片、非流式透传、失败日志、存储防御）。
`analyze-page.test.js` 加了「路线自带 idx/key/active」「高亮切换/越界不抛错」
「网关类网络失败不再误报成模型故障」「模板可渲染性静态守卫」等断言
（静态守卫会阻止以后再把 `{{index}}` 写回 `wx:for` 元素自身的属性）。
另外把 4 条硬性耗时断言放宽为「防性能回归」阈值（机器繁忙时曾误报 1 项失败）。

## 第二轮：预览里「生成点评」报 `request:fail abort`（已修）

用户反馈：预览里点「生成点评」仍然失败，文案是
`云端请求未能完成：… gateway_network_error · wx.request (chunked) failed: request:fail abort`。

**根因（上一轮自己引入的）**：适配器发现环境不给 `onChunkReceived` 后会
`probe.abort()` 掉探测请求再改走一次性请求。但**真实环境里 abort() 会回调
`fail({errMsg:'request:fail abort'})`** —— 这个由我们自己制造的 fail 抢先把整单判负，
`settle()` 的 `finished` 守卫于是把降级请求稍后拿到的正文直接丢掉。
**正文其实已经取到了，界面却报网络失败。**

**上一轮为什么没发现**：假 wx 的 `abort()` 只置了一个标志位、不回调 fail；
而且实网探针也没还原这个行为，所以「绿着通过」而真预览照样报错。**教训：打桩要还原真实行为。**

**修复**（`utils/workbuddy-cloud-diagnostics.js`）：
- `state` 增加 `owner`（谁结算的）与 `abandoned`（探测请求已被主动放弃）两个字段；
- `settle(owner, isFail, result)` 记录 owner；
- 新增 `abandonProbe(probe)`：置 `abandoned = true` → abort → **若探测请求在放弃前
  已同步结算过，把 `finished`/`owner` 复位**，让降级请求仍能结算；
- 探测请求的 `success`/`fail` 一进来先判 `state.abandoned`，是则直接 return；
- `chunkedSupported === false` 时直接走降级，不再白发一次探测请求。

**顺带把「用的哪个模型」这件事做清楚**（用户同时问了）：
- `llm.models.list()` 返回 **31 个模型**，含 `auto` / `default` 两个路由项；
- 原来的选法是「第一条 `disabled !== true`」，清单顺序一变就会悄悄换模型 ——
  改成**优先 `auto` → 再 `default` → 才退回第一条可用的**；
- 实测请求 `auto` 时服务端路由到 `hy4-preview`，
  **响应分片的 `chunk.model` 才是真正服务的模型**，已回传界面（`data.coachModel`），
  点评下方显示「本条点评由云端模型 xxx 生成」。

**实网端到端验证**（`cloud-live-probe.js`，已把假 wx 改成 abort 会回调 fail）：
真实云服务 + 预览式 wx → 31 个模型、**406 个分片 / 29s** 的真实中文点评、
`streamingStatus() === false`、分块探测只发 1 次 → 通过。

**测试**：`cloud-adapter.test.js` 新增第 3b 节「中止探测请求本身触发 fail 时，降级结果不能被丢弃」
（先跑出 FAIL 复现、再修成 PASS）；`analyze-page.test.js` 新增「界面显示实际服务的模型」
与第 11b 节「模型选择规则」（跳过停用、优先 auto、无 auto 时退回第一条、全停用时给可读提示）。
三套共 **201 项断言全绿**（44 + 121 + 36）。

技能 `~/.workbuddy/skills/miniprogram-preview-compat/` 已同步：修正示例代码，
新增「中止自己的探测请求 → request:fail abort」这一坑与打桩注意事项，
并补上模型选择规则。

## 第 4 轮：`request:fail timeout（云服务响应超时）` —— 看门狗定太紧 + 选错模型

用户反馈：点「生成点评」等了几十秒后仍是失败，错误行是
`gateway_network_error · wx.request (chunked) failed: request:fail timeout（云服务响应超时）`，
同时问「你是连接哪个大模型提供商的？」。

**复现**：写了 `cloud-model-probe.js`（用应用**真实的**教练提示词跑真实云服务），
在本机一模一样的复现：`durationMs: 50006`，即适配器自己的 50 秒兜底看门狗先开火。
那行括号里的中文就是我们自己写的，说明是时限问题，不是环境问题。
（注意：上一轮的实网探针用的是很短的提示词，只跑了 29s，所以没暴露。）

**根因（用 `cloud-model-bench.js` 量出来的）**：`auto` 路由到的是**思考型**模型
`hy4-preview-f`，同一段提示词：
- `auto` → **> 50s**，且 `max_tokens=360` 时 token 预算被思考吃光、**正文 0 字**；
- `deepseek-v4-flash` → **2905ms**（242 字）
- `hunyuan-chat` → **4980ms**（143 字）
- `glm-5.3-flash` → **10647ms**（234 字）

一个三五句话的点评，用思考型模型既慢又浪费额度。

**修法**
1. `ai-client.js`：`MODEL_PREFERENCE = ['deepseek-v4-flash','hunyuan-chat','glm-5.3-flash']`，
   之后才 `auto` / `default` / 第一条可用；跑通的模型缓存并排首位。
2. 请求加 `max_tokens: 480`；系统提示词补「150 字以内」。
3. **失败自动换模型重试一次**（`shouldTryNextModel`）：只重试 `timeout` / 空正文 / `model_*`；
   链路类、鉴权、额度、参数错误不重试；`signal.aborted`（用户取消）绝不重试。
4. 超时与「网络不通」分开报：`kind: 'timeout'`，判定要「code 是 `gateway_*` 且 detail 含 timeout」，
   文案「云端模型这次没有在限时内返回…可以再点一次」。
5. 适配器时限重定：一次性请求兜底 **75s**、`wx.request` 自身 timeout **80s**
   （略大于兜底，让可读文案先生效）；分块流式改成**空闲看门狗 25s / 每收到分片就重置**，
   不再用「从开始固定 45s」。自检要缩时限走 `createDiagnosticWx(wx, overrides)` 第二参。

## 第 5 轮：真机报 `TextDecoder is not defined` + 「怎么看错误详情」

用户把小程序放到**真机**上测试，点「生成点评」报 `TextDecoder is not defined`；

**根因**：云服务 SDK 的 SSE 解析器内部写死 `new TextDecoder('utf-8')`（**全局对象**），

**微信小程序运行时没有 TextDecoder** → 原生分块的第一个分片到达就抛错。
这是「预览绿、真机红」的典型：只看预览永远发现不了。

新增 `utils/text-codec.js`：
- `installTextCodec(scope?)` —— **只在缺失时安装**，绝不覆盖宿主已有实现；
  返回 `{installed, decoder, encoder, target}` 便于自检与界面提示；
- `Utf8TextDecoder` 支持 `new TextDecoder('utf-8')` / `decode(bytes)` /
  `decode(bytes, {stream:true})`（**跨调用保留被截断的多字节序列**）/ `decode()` 收尾；
  非法字节给 `U+FFFD` 不抛错；`Utf8TextEncoder` 一并补上。
- 安装点两处：`app.js` 启动时 + `utils/cloud.js` 顶部副作用 `require`（只要碰云服务就一定先补好）。
