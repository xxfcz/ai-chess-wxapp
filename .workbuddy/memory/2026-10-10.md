### 我提出并等待确认的方案

**入口形态**：新增轻首页（`pages/home`）+ `navigateTo`，**不用 wx tabBar**。
理由：analyze 页内已有 5 个 Tab（board/engine/coach/moves/log），再叠全局 tabBar = 两套 tab 概念；
tabBar 要求每项常驻独立页面且占约 50px 高度；子系统间是「任务切换」不是「并行浏览」。

**子系统划分（一个内核 + 四层外壳）**：按「局面从哪来 + 什么时候开口」划分，
不照搬 chess_tutor 的「对局/分析/学习」三分法（那是按活动类型分，会导致四套重复代码）。

| 子系统 | 局面来源 | 反馈时机 | 依赖引擎强度 | 优先级 |
|---|---|---|---|---|
| 沙盘分析（现有 analyze） | 用户粘 FEN / 手摆 | 用户主动问 | 是 | 已有，降为入口之一 |
| 战术闯关 | 题库 | 落子即判 | **否**（判定只比对答案） | 第一 |
| 棋局复盘 | 导入 PGN | 事后报告 | 强 | 第二 |
| 陪练对弈 | AI 对手 | 每步后 | 强（棋力+棋风） | 最后 |
| 开局训练 | ECO 8.6MB | 走偏即提示 | 否 | **建议不做** |

关键论据：
- 战术闯关是唯一绕开「端上引擎弱」短板的新子系统，且题库天然是打卡/付费点。
- 复盘必须两段式：浅搜扫一遍找「分数跳变点」→ 只对跳变点深搜。40 手全深搜在小程序上不可接受。
- 开局训练不做的理由：数据进不了包（8.6MB），且背谱对业余/少儿收益最低；
  真需要就做成「复盘时顺带标开局名」，成本近乎零。
- 陪练：`agent-plan.md §1.3` 已定棋风=评估权重、棋力=温度采样；建议做成「对局中可切到教练视角」，
  这是 chess_tutor 没做好的（它把下棋和讲棋塞进同一人格）。

**该抄的产品行为**（非代码）：走偏三选一（悔棋回谱/转对局/继续探索，泛化为岔路处理范式）、
每步漏招识别（6 类，需自建 300-500 行）、断点续练（小程序用 storage）、赛后报告。

**不该抄**：9 种教练人格（建议先做 2 个、放设置里而不是每次开局选）、12,379 条开局库。

### 追加：自建 Stockfish 服务 vs 云托管（同日第四轮）

用户提出第二条路：自建服务器跑 Stockfish。产出九项对比矩阵（域名备案/鉴权/冷启动/算力/
超时/低负载成本/常驻成本/运维/多端复用）。

**结论倾向自建**，三个决定性论据：

1. 云托管缩容到 0 后冷启动实测 20~40 秒，对「点一下等 2 秒」的分析场景是致命的；
   设最小副本=1 消掉冷启动后 ≈260 元/年（0.25核），成本优势就没了。
2. 0.25 核算力对 Stockfish 偏弱（要 depth 15~20 至少 1 核），加到 1核1G ≈760 元/年，
   已超过自建一台 2核2G。
3. 商业化项目迟早要可控后端（题库下发/用户系统/付费订单），自建机器的边际成本为零。

自建的门槛是 ICP 备案域名（7~20 工作日）+ 自建鉴权 + 公网防刷；
简化办法是把引擎做成「无状态无登录纯函数服务」，只做 IP 限流，AppSecret 都不用碰。
⚠️ 做 Web 版时禁止把 wasm 版 Stockfish 打进前端（那构成分发，GPL 复活）。

详见 `MEMORY.md` 的「自建 Stockfish 服务 vs 云托管」小节。

### 追加：讨论「能否用轻 LLM 替代端上分析」（同日第七轮，未采纳）

用户提出：`端上分析在任何环境下都可用` 这条硬要求可以不强求，改用轻量 LLM 代替端上分析。
**我反对，未改任何冻结条款，等用户决定。** 反方论据（含实测）：

**端上引擎实测耗时**（本机，node 22，`utils/engine.js`，multiPV=3）：

| 局面 | depth=2 | depth=3 | depth=4 |
|---|---|---|---|
| 起始局面 | 396ms / 10556 节点 | 415ms / 13117 | 793ms / 27253 |
| 中局（意大利开局后 3 回合） | 1294ms / 26648 | 2128ms / 47479 | 4457ms / 105164 |

页面默认 depth=2；`groundDemoLines` 用 `ai-client.js:419` 的默认 depth=3；换模型压 NNUE 才到 4。
对照组：LLM 单次往返实测 3~10s（plan §5.1）。**端上比 LLM 快 3~25 倍，零成本、离线可用。**

**三条反对理由（结构性，不是偏好）**：

1. **触发信号依赖本地评分。**「分数跳变超阈值」是四个 LLM 触发信号里最主要的一个。
   没有本地评分，这个信号消失 → 要判断"这步值不值得讲"只能每步都问 → **正好退回 chess_tutor**。
2. **评分不可校验。** 阶段一禁止 LLM 生成走法，是因为走法错了还能被 `resolveMoves` 校验出来；
   换成让 LLM 产出评分/最佳手，就没有任何校验器——比生成走法更隐蔽的幻觉。
   且 LLM 输出不可复现（同局面两次不同），无法做跨局比较，也没法给 UI 排稳定的 MultiPV 序。
3. **工具层会从"零延迟"变成"网络往返"。** plan §4.1 的 ReAct 预算模型假设工具调用零成本；
   `analyze()` 若走网络，一轮三次工具调用就是 10~30s，阶段二预算模型直接崩。

**澄清了一条可能的误解**：端上引擎不是待优化项，它是**冻结的基线**，`engine: remote` 接通后
自动让位，维护成本≈0。真正可以让 LLM 承担的是**解释层**——LLM 解释本地引擎，而非替代本地引擎。
若确实要"无本地评分也能讲"，正确做法不是让 LLM 猜分，而是**降级为无分数的定性讲解**
并明确告知用户"本次无引擎评分"。

**可接受的折中**（待用户拍板）：改措辞不改保证——把 AGENTS.md §8 的
「端上分析在任何环境下都可用」精确化为「**规则判定、走法生成、演示线、本地评分这四条保底通道
不依赖网络，任何环境下都必须可用**」。
