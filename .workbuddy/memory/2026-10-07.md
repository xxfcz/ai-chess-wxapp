# 2026-10-07

## 讨论：把国象分析小程序升级为 AI Agent 的思路（未动手改代码）

结论：现有实现已是「Agent 胚胎」（感知 FEN → 端上引擎推理 → 给建议/演示线 → 用户走子反馈），
缺的是**工具协议、自主循环、记忆**三样。

核心观点记录：
1. **最大技术债是让 LLM 生成 SAN**。`ai-client.js` 的 COACH_SYSTEM_PROMPT 用大段文字约束
   "走法必须合法、不许编造"，本质是用提示词对抗幻觉。Agent 化后应改为：模型只输出**意图**，
   走法序列 100% 由 chess.js 生成，幻觉归零，这段 prompt 可删一半。
2. **端上引擎是天然工具层**（零延迟/零成本/离线/可高频调用），LLM 只做规划与表达。
   候选工具：`analyze(fen,depth,multiPV)`、`legal_moves(fen,sq)`、`expand_line(fen,moves[])`、
   `describe(fen)`（子力/王安全/兵型结构化特征）。
3. 落地分三步，**推荐先做阶段一**：把 `===DEMO===` 从"模型凭空生成"改成"模型提意图 →
   端上生成合法序列"，保留单次 LLM 往返，复杂度 +20% 拿 80% 收益。阶段二开放多轮 ReAct（须配
   预算：最多 3 轮工具调用 / N 次 analyze / 总时长 30s 上限）。阶段三加记忆层（云 DB 按 openid：
   棋力画像、错题本、本局话题）。
4. 工程约束继承：工具结果压缩后再回传（只回分数差 + 关键 2-3 手）；单次会话锁定模型（复用
   `cachedModelId`）；重试策略从"单次请求"上提到"会话层"（`shouldTryNextModel` 要重做粒度）；
   超时预算按整局分配，cloud-adapter 的流式/TextDecoder/看门狗坑每轮都会遇到。
5. 产品形态三选一：A 小程序内多轮教练（最贴合现有代码）/ B 对外 MCP 或微信客服服务 /
   C 会下棋的对手 Agent（本质是评估函数调参，应与 A 分开做）。

## 用户决策：优先 A（小程序内多轮教练），其次 C（会下棋的对手 Agent），B 暂不做

## 关键前提核查（影响技术路线，已实测）

### 本项目实际链路（重要，决定了哪些限制适用）

```
小程序 → @tencent-ai/workbuddy-cloud-sdk → HTTPS 直连 mp-api.app.workbuddy.host → WorkBuddy LLM 网关
```
- **没有 `cloudfunctions/` 目录**、没有 `wx.cloud.callFunction`、没有 `wx.cloud.extend.AI`、
  没有 `@cloudbase/node-sdk`。package.json 唯一依赖就是 workbuddy-cloud-sdk。
- ⇒ 微信云开发体系的所有硬限制（云函数超时 1–900s / 请求响应体各 6MB /
  云托管链路小程序端 100KB 且 ≤15s / 并发按套餐分级）**对本方案一个都不适用**。
- 真正适用的是 **WorkBuddy LLM 网关侧的超时**（ai-client 现有 30s 兜底 + CHUNK_IDLE 看门狗）
  和 **网络 RTT**。端上工具本身零耗时，所以多轮 ReAct 的瓶颈全在往返次数上。

### 原结论的精确措辞（此前表述有歧义，已订正）

❌ 错的说法：「云服务 SDK 不支持 function calling」——容易被读成"微信不支持"。
✓ 正确说法：**本项目使用的 `@tencent-ai/workbuddy-cloud-sdk v0.1.2` 这个第三方客户端 SDK
  未暴露 LLM tool-calling 能力**（静态扫描 `miniprogram.js`：`tools`/`tool_calls`/`toolChoice` 均为 0 次，
  命中的 `function_call` 全是 core-js 内部实现）。

补充事实（元宝核）：CloudBase AI Node SDK ≥3.16.0 有 `registerFunctionTool`；
小程序端 `wx.cloud.extend.AI`（基础库 ≥3.7.1）也支持 tool calling；`wx.cloud.callFunction`
至今仍是云函数调用的官方方式。但这三者本项目都没引入，不改变本项目的技术选型。

两个可用口子：
- `ChatCompletionsAPI.createStreaming` 是 `const { signal, conversationId, ...body } = input`
  后**整个 body 原样 JSON.stringify 透传**到 `/chat/completions`，且 chunk 是 `yield chunk` 原样吐出。
  → 手工塞 `tools` 参数理论上可行，但**网关是否转发未经证实，必须实网探针验证**。
- 支持 **`conversationId`**（→ `X-Conversation-ID` 请求头）：多轮会话的官方通道，阶段二直接用。
- `models.list()` 返回的条目里有 **`supportsToolCall`** 布尔字段 —— 可据此筛出候选模型再验证。

**`coach-demo.js` 的兜底比想象中靠前**：
`resolveMoves()` 已逐手 `Game.applySan` 校验，非法就 console.warn + 截断保留合法前缀，全废才丢整条。
所以现状不是"幻觉走法上盘"，而是**模型一猜错推荐线就被截断/消失、正文链接跟着失效**。
改造点因此更明确：把"事后校验"前移成"候选预生成 + 模型只做选择"。

**质量门禁目前是空的**：AGENTS.md 声称的 `.workbuddy/tests/` 三个回归脚本
（engine-and-game / analyze-page / cloud-adapter）**磁盘上不存在**，`.workbuddy/` 下当时只有刚建的
memory 目录。做任何改造前建议先把这三套测试补回来。

### 写测试过程中发现并修掉的 3 个生产 bug

1. **`utils/game.js#load` 不接受缺字段的 FEN**（真 bug，UI 已承诺「只写布局自动补全」却静默失败）。
   加 `normalizeFenFields()`：不足 6 段且首段匹配 `/^([1-8pnbrqkPNBRQK]+\/){7}...$/` 时才补全；
   对乱码**保持原样**，否则会把「布局段非法」误报成「行棋方非法」，掩盖真因。
2. **`workbuddy-cloud-diagnostics.js#startPlainFallback` 缺 try/catch**。
   探测请求有保护、降级请求没有——`wx.request` 在降级这步抛错会直接穿透给用户，SDK 连 fail 都收不到。已补上并走 `settle('plain', true, ...)`。
3. **`utils/ai-client.js` 未导出 `shouldTryNextModel`**。
   它恰恰是 Agent 化阶段二要重写的核心（重试粒度要从「单次请求」上提到「会话层」），导出以便有回归兜底。

### 角色命名（用户最终拍板，会影响每个 trade-off）

- **教练 = Tutor**（`tutor`）—— 本轮聚焦
- **陪练 = Sparrer**（`sparrer`）—— 占位，未立项
  - 词典常见拼写是 `sparer`，本项目**统一双写 r 作 `sparrer`**，当项目术语固定。
  - 早先建议的 `sparring partner` 语义最准但**两个词带空格**，进标识符/存储键很笨重；
    `sparrer` 语义相同且是单个小写词，可直接用作标识符。
- **不用 `opponent` / `rival`**。理由不是文字游戏：`opponent` 的目的是赢你，用它命名会让产品
  不自觉往"提高胜率"优化，结果是用户每局被虐；`sparrer` 的目的是让你练到东西，
  最优解是"刚好比你强一点、恰好在你薄弱处施压"。命名会在每个设计取舍里起作用。
  （`opponent` 仍可作普通名词指棋局对方，但不指本产品角色。）

### 术语与既有代码的关系（本文档 §1.4，容易踩的坑）

**新增代码用新名，既有 `coach` 标识符不重命名**：`COACH_SYSTEM_PROMPT`、`utils/coach-demo.js`、
`onCoach`、`coachText`、`ai.requestCoachComment()` 全部保留——改名收益低、回归风险高
（`coachText` 还是 setData 键名，牵动 WXML）。等将来整体重写 `ai-client.js` 时顺手统一。
真正要避免的是「同一个概念在新代码里一半叫 coach、一半叫 tutor」。

阶段三代号同步由 `Persistent Coaching Memory` 改为 **`Persistent Tutoring Memory`**。

### 三阶段

| | 代号 | 一句话 |
|---|---|---|
| 一 | Candidate Grounding | 模型提意图 → 端上生成合法序列 |
| 二 | Reason-Act Loop | 多轮 ReAct，配硬预算 |
| 三 | Persistent Tutoring Memory | 棋力画像 / 错题本 / 话题主线 |

### 用户的过程要求：不要预先写死函数级"改造清单"

理由是对的——代码会变，提前定死会成为维护负担。**改成保留「契约清单」**：
- ❌ 删掉：`ai-client.js` 第 N 行改成…（一改就失效）
- ✅ 保留：`legalMoves(fen, sq) → [{uci, san, ...}]`（这是协议，提前冻结反而防返工）
阶段一保留较具体的落地清单（近期开工、结论已收敛）；阶段二、三只留**契约 + 待决策项 + 验收口径**。
另用 D1~D10 决策条目记「为什么这么定」——半年后想推翻接口时需要的是当初的理由。

### 阶段一的一个关键结论

候选生成**不需要额外跑搜索**：页面点评时 `this._lastResult` 已有三条线及各自 PV，
复用即可（比早先设想的"跑一次浅搜索"更省，额外成本 ≈ 0）。仅在缺失时才补跑。
`===DEMO===` 演进为 `cand`（候选编号）+ `extend`（端上继续展开几手），模型**完全不碰走法**；
保留旧 `moves` 字段作向后兼容路径，现有 `resolveMoves` 校验一行不动（降级为几乎不触发的最后防线）。

## 梳理：Tutor 与用户的交互过程与讲解维度（讨论，暂未落文档）

一次典型辅导会话七步：摆局面 → 端上引擎给三条线（现状） → 点生成点评 → 讲解+演示线（阶段一）
→ 追问「为什么 Nc3 不行」 → 自己验算后拿证据回答（阶段二） → 下一局仍记得你栽在哪（阶段三）。
**断裂点在第三、四步之间**：现在拿到建议后无法追问，产品也不知道用户为什么这么走。

### 九个讲解维度（决定了各自何时可用）

关于局面：形势判断（现状有数字，阶段一才有解释）、走法比较、因果解释、威胁识别、计划验证、
战略取舍（后五个全靠 `expand_line`/`compare_moves`/`why_bad`，**阶段二才是价值拐点**）。
关于用户：错误归因（阶段二）、改善跟踪、因人施教（阶段三）。

⇒ 结论：关于局面的六个维度里五个卡在同一处——需要「沿某条线走下去看会发生什么」。
所以阶段一是把现有功能做可靠，阶段二才真正带来新能力。

### 四种教学姿态（容易被忽略的产品差异点）

讲（现状唯一有）/ 演（有但阶段一才可靠）/ **问（目前完全没有）** / 练（阶段三）。

「问」= 苏格拉底式：不吐答案只给线索（「数数黑方有几个子在打 e4？」）。棋力提升靠自己算，
AI 棋类产品的默认姿态全是「讲」，这是同質化最严重也最容易做出差异的地方。

## 已落档：docs/agent-tutor-interactions.md（交互总览，406 行）

**定位：** 三份阶段文档讲「系统怎么做」，本篇讲「用户看到什么、能做什么、出错时听到什么」。
之所以单独成文：三个阶段的界面增量会累积，不提前统一口径阶段三必返工。**只冻结交互契约与文案口径，不写实现清单。**

六条交互第一性原则（不可妥协程度排序）：
1. **Tutor 必须能「指」棋盘** —— 否则它只是会说话的文本区，不如直接用通用大模型。
   现有 move/sq/piece 三类富文本记号 + 紫色 focus 高亮是**资产不是包袱**。
2. 棋盘主权不可侵犯 —— 只有演示态能接管棋盘，且必须临时副本 + 面包屑 + 一键退出。
3. 过程可见但**原始**过程不可见 —— 「正在验算第 2 步」给，JSON/FEN/工具名不给（那是运行日志 Tab 的活）。
4. 宁慢勿错 ⇒ UI 必须能优雅承载 15~30s 等待。
5. 任何时刻可中断，中断后零请求；**中断不得以错误态呈现**。
6. 失败必须可归因，`服务繁忙请稍后再试` `AI出错了` 列为**禁用词**。

几个结论：
- **明确否决聊天窗口**（三个理由：挤占棋盘 / 与本页「Tab 内不再各自滚动」架构正面对撞 / 有更好做法）。
  采纳「同 Tab 内对话卡片流」：最近 3 轮、(`scroll-into-view` 可用，不依赖缺失的 createSelectorQuery)、
  输入框放 Tab 底部而非吸底栏（会和底部 5 个 Tab 打架）。**三个阶段都不新增底部 Tab。**
- **快捷提问比输入框重要**，且问句本身可由端上生成（候选池 top-2 分差小 →「为什么推荐 #1 而不是 #2？」）。
- **教学姿态四档：讲 / 演 / 问 / 练**（写入文档 §1.7）。「问」= 苏格拉底式，当前完全没有，是同质化最严重
  也最值得做的一档；但必须可退让（用户答不上来就立刻切回「讲」）。
- **记忆必须允许用户纠错**（写进 §6.2）——画像从行为推断必然有误，没有纠错通道的标签会一直错下去。
- 文档 §2.1 列了 6 个交互病灶（I1~I6），其中 **I6 是性能型**：`onDelta` 每个分片 setData 全文且每片跑一次
  `stripDemoBlock` → O(n²)。建议 ≥120ms 节流。I4 = 已知的 view() 字段名不一致。

另外：本篇不含此前讨论的「九个讲解维度」全表，只保留了由此得出的阶段价值判断
（六个维度里五个都卡在「沿某条线走下去」，所以阶段二才是价值拐点）。
