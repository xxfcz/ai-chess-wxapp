# 2026-10-07

## 讨论：把国象分析小程序升级为 AI Agent 的思路（未动手改代码）

结论：现有实现已是「Agent 胚胎」（感知 FEN → 端上引擎推理 → 给建议/演示线 → 用户走子反馈），
缺的是**工具协议、自主循环、记忆**三样。

核心观点记录：
1. **最大技术债是让 LLM 生成 SAN**。`ai-client.js` 的 COACH_SYSTEM_PROMPT 用大段文字约束
   "走法必须合法、不许编造"，本质是用提示词对抗幻觉。Agent 化后应改为：模型只输出**意图**，
   走法序列 100% 由 chess.js 生成，幻觉归零，这段 prompt 可删一半。
2. **端上引擎是天然工具层**（零延迟/零成本/离线/可高频调用），LLM 只做规划与表达。
   候选工具：`analyze(fen,depth,multiPV)`、`legal_moves(fen,sq)`、`expand_line(fen,moves[])`、
   `describe(fen)`（子力/王安全/兵型结构化特征）。
3. 落地分三步，**推荐先做阶段一**：把 `===DEMO===` 从"模型凭空生成"改成"模型提意图 →
   端上生成合法序列"，保留单次 LLM 往返，复杂度 +20% 拿 80% 收益。阶段二开放多轮 ReAct（须配
   预算：最多 3 轮工具调用 / N 次 analyze / 总时长 30s 上限）。阶段三加记忆层（云 DB 按 openid：
   棋力画像、错题本、本局话题）。
4. 工程约束继承：工具结果压缩后再回传（只回分数差 + 关键 2-3 手）；单次会话锁定模型（复用
   `cachedModelId`）；重试策略从"单次请求"上提到"会话层"（`shouldTryNextModel` 要重做粒度）；
   超时预算按整局分配，cloud-adapter 的流式/TextDecoder/看门狗坑每轮都会遇到。
5. 产品形态三选一：A 小程序内多轮教练（最贴合现有代码）/ B 对外 MCP 或微信客服服务 /
   C 会下棋的对手 Agent（本质是评估函数调参，应与 A 分开做）。

## 用户决策：优先 A（小程序内多轮教练），其次 C（会下棋的对手 Agent），B 暂不做

## 关键前提核查（影响技术路线，已实测）

### 本项目实际链路（重要，决定了哪些限制适用）

```
小程序 → @tencent-ai/workbuddy-cloud-sdk → HTTPS 直连 mp-api.app.workbuddy.host → WorkBuddy LLM 网关
```
- **没有 `cloudfunctions/` 目录**、没有 `wx.cloud.callFunction`、没有 `wx.cloud.extend.AI`、
  没有 `@cloudbase/node-sdk`。package.json 唯一依赖就是 workbuddy-cloud-sdk。
- ⇒ 微信云开发体系的所有硬限制（云函数超时 1–900s / 请求响应体各 6MB /
  云托管链路小程序端 100KB 且 ≤15s / 并发按套餐分级）**对本方案一个都不适用**。
- 真正适用的是 **WorkBuddy LLM 网关侧的超时**（ai-client 现有 30s 兜底 + CHUNK_IDLE 看门狗）
  和 **网络 RTT**。端上工具本身零耗时，所以多轮 ReAct 的瓶颈全在往返次数上。

### 原结论的精确措辞（此前表述有歧义，已订正）

❌ 错的说法：「云服务 SDK 不支持 function calling」——容易被读成"微信不支持"。
✓ 正确说法：**本项目使用的 `@tencent-ai/workbuddy-cloud-sdk v0.1.2` 这个第三方客户端 SDK
  未暴露 LLM tool-calling 能力**（静态扫描 `miniprogram.js`：`tools`/`tool_calls`/`toolChoice` 均为 0 次，
  命中的 `function_call` 全是 core-js 内部实现）。

补充事实（元宝核）：CloudBase AI Node SDK ≥3.16.0 有 `registerFunctionTool`；
小程序端 `wx.cloud.extend.AI`（基础库 ≥3.7.1）也支持 tool calling；`wx.cloud.callFunction`
至今仍是云函数调用的官方方式。但这三者本项目都没引入，不改变本项目的技术选型。

两个可用口子：
- `ChatCompletionsAPI.createStreaming` 是 `const { signal, conversationId, ...body } = input`
  后**整个 body 原样 JSON.stringify 透传**到 `/chat/completions`，且 chunk 是 `yield chunk` 原样吐出。
  → 手工塞 `tools` 参数理论上可行，但**网关是否转发未经证实，必须实网探针验证**。
- 支持 **`conversationId`**（→ `X-Conversation-ID` 请求头）：多轮会话的官方通道，阶段二直接用。
- `models.list()` 返回的条目里有 **`supportsToolCall`** 布尔字段 —— 可据此筛出候选模型再验证。

**`coach-demo.js` 的兜底比想象中靠前**：
`resolveMoves()` 已逐手 `Game.applySan` 校验，非法就 console.warn + 截断保留合法前缀，全废才丢整条。
所以现状不是"幻觉走法上盘"，而是**模型一猜错推荐线就被截断/消失、正文链接跟着失效**。
改造点因此更明确：把"事后校验"前移成"候选预生成 + 模型只做选择"。

**质量门禁目前是空的**：AGENTS.md 声称的 `.workbuddy/tests/` 三个回归脚本
（engine-and-game / analyze-page / cloud-adapter）**磁盘上不存在**，`.workbuddy/` 下当时只有刚建的
memory 目录。做任何改造前建议先把这三套测试补回来。

### 写测试过程中发现并修掉的 3 个生产 bug

1. **`utils/game.js#load` 不接受缺字段的 FEN**（真 bug，UI 已承诺「只写布局自动补全」却静默失败）。
   加 `normalizeFenFields()`：不足 6 段且首段匹配 `/^([1-8pnbrqkPNBRQK]+\/){7}...$/` 时才补全；
   对乱码**保持原样**，否则会把「布局段非法」误报成「行棋方非法」，掩盖真因。
2. **`workbuddy-cloud-diagnostics.js#startPlainFallback` 缺 try/catch**。
   探测请求有保护、降级请求没有——`wx.request` 在降级这步抛错会直接穿透给用户，SDK 连 fail 都收不到。已补上并走 `settle('plain', true, ...)`。
3. **`utils/ai-client.js` 未导出 `shouldTryNextModel`**。
   它恰恰是 Agent 化阶段二要重写的核心（重试粒度要从「单次请求」上提到「会话层」），导出以便有回归兜底。

### 已知缺陷（已用测试钉住，暂未修）

`coach-demo.js` 的 `DemoSession.view()` 返回 `active/breadcrumb/canBack/canForward/playing`，
而 `analyze.wxml` 读的是 `demoActive/demoBreadcrumb/demoCanBack/demoCanForward/demoPlaying`。
字段名不一致——演示线的控制按钮大概率是失效的。**开 A 阶段一时应顺手统一**。
