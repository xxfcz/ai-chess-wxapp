# 阶段三 · Persistent Tutoring Memory（持续教练记忆）

> 让 Tutor 从「每次都是陌生人」变成「记得你是谁、上次栽在哪」。
> 总纲见 `docs/agent-plan.md`；依赖阶段二确定的会话结构。
>
> 与阶段二同理，本篇**不写函数级改造清单**。这里冻结的是**数据形态、隐私边界与验收口径**。

---

## 1. 目标

前两个阶段解决的是「这一次讲得准不准」。阶段三解决的是：

> **每一次的讲解能不能相互累积。**

今天每次点「生成点评」都是全新开始：同一个用户第三十次问「为什么我被农家将杀」，
Agent 依然从头讲一遍基础——因为它不记得第二十九次。

阶段三要存三类东西：

| 类别 | 内容 | 用户可感知的价值 |
|---|---|---|
| **棋力画像** | 从错误类型推断的水平与倾向 | 讲解深度自动适配；不再用初级词汇解释你已经懂的东西 |
| **错题本** | 反复犯的错、被 KA 反复吃到的战术 | 「你在这个形状上第三次丢子了」 |
| **话题主线** | 本局已经讲过什么 | 避免重复讲同一件事造成的唠叨感 |

## 2. 产品设计

### 2.1 三条记忆线的具体形态

#### ① 棋力画像（Skill Profile）

**关键原则：从行为推断，不靠用户自评。**

用户在设置里选「我是中级」几乎没有信息量——绝大多数人对自己的评价都偏离实际。
更好的输入是**他从实战中犯的错**：

```
观察到的错误分布（近 N 局）：
  忽略对手威胁（blunder 漏看）    ████████  42%
  残局基本技术（王兵 vs 王）       ████     23%
  出子过慢、重复走同一子          ███      17%
  战术识别（叉/串/牵）            ██       12%
  其它                            █        6%
```

由此推出两条产品行为：

- **讲解深度自适应**：残局技术弱的用户，在残局得到更细的分解步骤；
- **主动提醒**：某类错误占比上升时，在新点评里顺带一句（「这里我们上次也漏过对手的f7 威胁」）。

#### ② 错题本（Mistake Ledger）

每条记录的核心是**可复用的失败模式**，而不是某一局的具体走法：

```js
{
  pattern: 'ignored_back_rank',          // 失败模式的稳定标识
  occurrences: 3,
  firstSeenAt, lastSeenAt,
  sampleFens: [...],                     // 最多保留 3 个样本，够用又不至于臃肿
  resolution: 'pending' | 'improving'    // 最近是否还在犯
}
```

判定「改善了」很重要：**只记不改会让用户感觉被反复翻旧账。**

#### ③ 话题主线（Topic Ledger）

本局已经讨论过的话题，避免重复：

```
已讲：中心争夺（开局第 4 手）、f7 弱点
未讲：后翼 Nr 的出子路线 —— 这是本次点评可以接续的方向
```

### 2.2 隐私与可控性（不可妥协）

这是本阶段**唯一没有商量余地**的部分：

| 原则 | 具体要求 |
|---|---|
| **按 openid 隔离** | 一人一份，服务端不得跨用户聚合用于其他目的 |
| **可见** | 用户能在界面上看到系统对自己的画像（不是黑箱打分） |
| **可清除** | 一键清除全部记忆；清除后立即停止使用，并确认真删除 |
| **可导出** | 至少提供查看方式；导出能力建议做，成本很低 |
| **默认安全** | 记忆只存棋类相关特征；**不存**对话原文、位置、设备信息等无关内容 |

> 产品判断：**把画像显示给用户本身就是价值。**
> 绝大多数棋手从没见过自己错误类型的分布图——即使不给任何 AI 建议，光这张图就有吸引力。

## 3. 需求说明

| # | 需求 | 验收方式 |
|---|---|---|
| **R1** | 棋力画像从**实际对局行为**推断，不依赖用户自评 | 单测：喂入构造好的错误序列，断言画像输出落在预期维度 |
| **R2** | 画像对用户**可见** | 界面能展示错误分布，且文案不含贬义评判 |
| **R3** | 一键清除且**确认真删除** | 单测：清除后再请求返回空，且服务端返回明确确认 |
| **R4** | 错题本能识别「已改善」并停止反复提及 | 单测：构造「近期不再犯」的序列，断言 status 转 improving |
| **R5** | 同一局面连续点评**不重复**讲同一话题 | 场景集：连续两次点评，第二次必须引入新话题或明确表示「上一次已讲」 |
| **R6** | 记忆失败不影响主体功能 | 单测：存储读写抛错时，点评仍能正常产出（记忆是增强，不是前提） |
| **R7** | 存储成本可控 | 单测：单用户记忆体量上限，超出按策略淘汰 |
| **R8** | **不存**对话原文 | 静态检查 + 单测：写入前过滤器拦截非棋类字段 |
| **R9** | 端上能力不因记忆层故障降级 | AGENTS.md §8：记忆层挂掉，引擎分析与单次点评照常 |
| **R10** | 三套既有回归 + 阶段一/二测试全绿 | 门禁命令见总纲 §7.1 |

## 4. 系统设计

### 4.1 分层

```
┌────────────────────────────────────────┐
│ 写入侧：每一局/每一次点评之后             │
│   抽取事件 → 归并到模式 → 更新画像        │
└──────────────┬─────────────────────────┘
               ▼
┌────────────────────────────────────────┐
│ 存储：云 DB（按 openid）+ 端上缓存        │
│   端上缓存用于离线读取与减少读请求          │
│   写操作允许延迟/失败重试，读入失败则降级  │
└──────────────┬─────────────────────────┘
               ▼
┌────────────────────────────────────────┐
│ 读取侧：构造点评时作为上下文               │
│   压缩成几句陈述，拼进 system/user prompt  │
└────────────────────────────────────────┘
```

**写入的关键设计：不要尝试实时写。** 点评是流式且可能中途放弃的，
在每次点评后同步写一次，延迟可接受、实现简单、失败也好重试。

### 4.2 上下文注入的形态

给 LLM 的记忆应尽量**压缩且去敏感化**：

```
关于这位用户（仅作参考，不要在点评里直接复述这些标签）：
- 近 12 局最常见的失误是漏看对手威胁（约 4 成）
- 残局基本技术偏弱
- 本局已讨论过：中心争夺、f7 弱点
- 尚未讨论：后翼出子路线
```

三条纪律：

1. **不让模型复述标签**——用户不该在自己的点评里读到「你属于漏看型选手」这种判词；
2. **记忆是提示不是指令**——记忆过期或失准时，模型的判断应能覆盖它；
3. **压缩到 5 行以内**——每多一个 token 都是延迟，而且过量的记忆会稀释当前局面的信息。

### 4.3 降级策略

| 故障 | 行为 |
|---|---|
| 云 DB 读失败 | 用端上缓存；无缓存则**当作新用户**，点评照常产出 |
| 云 DB 写失败 | 记日志，**静默重试一次**，不打扰用户 |
| 画像数据损坏/版本不符 | 丢弃重建，不尝试迁移脏数据 |
| 用户已清除 | 所有读取返回空，不再有任何历史引用 |

## 5. 契约

```js
// 记忆主体的建议形态（字段名待定，形状先定）

MemoryProfile = {
  version: number,
  updatedAt: number,
  skills:   { [dimension: string]: { score: number, samples: number, trend: 'up'|'flat'|'down' } },
  mistakes: [ MistakePattern ],
  recency:  { lastSessionAt: number, totalGames: number }
}

MistakePattern = {
  pattern: string,           // 稳定标识，如 'ignored_back_rank'
  occurrences: number,
  firstSeenAt: number,
  lastSeenAt: number,
  status: 'pending' | 'improving',
  sampleFens: string[]       // 上限 3
}
```

```js
// 对外接口（形状）

memory.load(openid)        → MemoryProfile | null
memory.record(openid, events) → void          // 幂等；失败不抛
memory.summarize(profile, currentFen) → string // 压缩成 prompt 用的几行
memory.clear(openid)       → boolean          // 确认真删除
```

> `version` 字段必留：第一阶段上线后几乎必然会调整数据形态，
> 有版本号才能优雅地丢弃旧数据而不是写一堆迁移逻辑。

### 5.1 错误维度建议起点

先定五个维度跑起来，不要一上来就设计几十个标签：

| 维度 | ident | 典型信号 |
|---|---|---|
| 漏看对手威胁 | `missed_threat` | 走子后立刻被吃子且无补偿 |
| 残局技术 | `endgame_technique` | 残局阶段评分大幅滑落 |
| 出子效率 | `development` | 开局重复走同一子、滞后出子 |
| 战术识别 | `tactics` | 错过可用的叉/串/牵 |
| 王安全 | `king_safety` | 王翼被打开后未处理 |

## 6. 待决策项（留白）

| # | 待决策 | 取决于 |
|---|---|---|
| Q1 | 用哪个存储：云 DB vs 端上 Storage | 是否需要跨设备同步；若无该需求，端上更简单且零成本 |
| Q2 | 画像「衰落」的处理：旧数据是否按时间衰减 | 棋力会变化；不衰减的话一年的数据会淹没近期的进步 |
| Q3 | 是否把画像暴露给 LLM（隐私 vs 个性化强度） | 可在 Q1/R2 上线后按用户反馈决定粒度 |
| Q4 | 错题本是否需要在 UI 上单独成页 | 观察用户是否真的会去看——很多健身类产品的教训是没人看第二屏 |
| Q5 | 「下一次该讲什么」是否由 Agent 主动提出 | 产品判断；与阶段二 Q6 相关 |
| Q6 | 冷启动：新用户前几局给什么深度 | 可用「先按中级，快速收敛」的默认策略 |

## 7. 验收

### 7.1 场景集

| 场景 | 期望 |
|---|---|
| 新用户首局 | 不出现任何「你上次/你通常」的表述 |
| 连续三局同类错误 | 第三局画像出现该维度，且点评用词更针对它 |
| 用户此后不再犯该错 | 状态转 improving，点评停止反复提 |
| 点击「清除我的记忆」 | 后续点评恢复成新用户语气；且服务端确认删除 |
| 存储不可用 | 点评照常产出，无报错文案露出 |
| 同一局面连续点评两次 | 第二次不重复第一次已讲的话题 |

### 7.2 红线

- **任何情况下不得存储对话原文**；
- 记忆故障**永远不得**让四条保底通道（AGENTS.md §8）与单次点评失效；
- 清除操作必须是**真删除**，不是标记删除。

---

## 8. 风险

| 风险 | 影响 | 提前预防 |
|---|---|---|
| **画像漂移**：早期样本少导致误判，用户被贴错标签 | 讲解方向整体跑偏 | 样本数阈值：少于 N 局不输出强判断；R2 让用户看得见，可自行忽略 |
| 反复翻旧账引起反感 | 用户关闭功能甚至弃用 | R4 的 improving 判定；同一模式在短期内最多提醒一次 |
| 隐私争议 | 最高级别的风险 | §2.2 五条原则作为硬门槛，任何一条不满足就不上线 |
| 存储成本随用户增长 | 成本不可控 | R7 体量上限 + 淘汰策略（sampleFens 仅限 3 条） |
| 记忆失真或过期数据干扰当前局面判断 | 答非所问 | §4.2 纪律 2：记忆是提示不是指令；且压缩到 5 行以内 |
| 模型把标签直接说给用户听 | 体验伤害（用户感到被评判） | §4.2 纪律 1；并在 system prompt 明确禁止复述 |
