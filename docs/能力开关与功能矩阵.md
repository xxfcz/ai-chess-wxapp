# 能力开关与功能矩阵

> 制定日期：2026-10-10　·　决策编号：`agent-plan.md` §6 的 D12 / D13
>
> 本文档是本项目**唯一的**能力分级方式。此前讨论中出现的 L0 / L1 / L2 / L3 / L4 线性档位
> **已废弃，全项目不再使用**——文档与代码里出现即视为笔误。

---

## 1. 三个开关

| 开关 | 取值 | 含义 | 当前 |
| --- | --- | --- | --- |
| `engine` | `local` \| `remote` | 端上 JS 引擎 / 远程真引擎（Stockfish） | `local` |
| `cloud` | `off` \| `on` | 有无原生云（DB / 存储 / 题库下发） | `off` |
| `llm` | `off` \| `light` \| `heavy` | 大模型参与度 | 取决于云服务可达性 |

**为什么 `engine` 用 `remote` 而不是 `cloud`**：`cloud` 在本项目语境里已经被「微信原生云 / 云开发」
占用了，两个概念同名会持续制造歧义。而远程引擎的实现路径不止一种——微信云托管容器
（managed container）、自建 VPS、第三方 API 都算。用 `remote` 只表达「不在端上跑」这一件事，
与是否用微信云无关。

**矩阵里为什么不单列 `off`**：`off` 是基线，含义就是「这项能力缺失 / 产品不讲话」。
为它单开一列没有信息量，反而会把「开到什么程度才有变化」这个真正的问题挤掉。

### 1.1 「引擎」这个词盖住的三样东西

常说错的一句话是「本地没有引擎」。**更准确的说法是：本地有一个弱引擎。** 拆开看：

| 层 | 具体是什么 | 准确性 | 归谁管 |
| --- | --- | --- | --- |
| 规则层 | chess.js：合法走法生成、将军 / 将死 / 终局判定 | **100% 确定，零误差** | 不受任何开关影响（矩阵里标 `—`） |
| 搜索 + 评估层 | `utils/engine.js`：Alpha-Beta + 静态评估 + 静态搜索 + MultiPV | **启发式**，棋力约业余水平 | 这才是 `engine` 开关在切换的东西 |
| 输出层 | 三条路线、`scoreCp`、PV | 是**结果**，不是能力 | 随上面一层变化 |

由此三条：

1. **规则判定不是引擎**，是引擎的地基。它零误差，任何开关组合下都一样。
2. **PV 走法不是引擎**，是引擎的输出。拿输出当能力，等于说「GPS 画的路线就是发动机」。
3. **`engine: local` 与 `engine: remote` 的差别是强度（弱 vs 强），不是有无。** 两端都有引擎。

两条落到产品上的约束：

- **文案上不许说"无引擎 / 无法分析"。** 离线时三条线、评分、演示线照样能出，
  应该说「本地引擎棋力有限，评分仅供参考」。
- **规则判定与引擎评分必须在界面上分层。** 前者是事实（可以断言"这步不合法"），
  后者是意见（只能说"引擎认为…"）。混在一起会让用户把启发式评分当成确定性事实——
  而本地引擎恰恰是最容易错的那一个。

## 2. 为什么不用单一档位

曾经试过用 L0~L4 一条线性阶梯（本地 → 有云 → 有 Stockfish → 加轻 LLM → 加重 LLM），废弃原因有三：

1. **最常见的真实组合在阶梯上没有位置。** `cloud on + engine local + llm light`
   （有云、有大模型、没 Stockfish）是零成本就能达成的配置——LLM 走现有免 Key 云服务几乎不花钱，
   Stockfish 却要另开环境。它在阶梯里只能被判成中间档，于是**点评入口被误隐藏**，
   而事实上它完全能用。
2. **阶梯隐含"高档位包含低档位"，但这里不是包含关系。** 加了远程引擎不代表有了云存储，
   开了重 LLM 也不代表引擎变强。三者正交。
3. **功能点之间的依赖关系不一样。** 「棋盘走子」三个开关都不看；「逐手评分找漏招」只看 `engine`；
   「错题记忆」要看 `cloud` + `llm`。用一条全局档位去判定这些，必然出错。

因此规则只有一条：

> **每个功能点按自己依赖哪个开关渲染，不要问"全局是第几档"。**

## 3. 功能矩阵

图例：**●** 完整　**◐** 降级可用　**○** 缺失（该取值下没有这项能力）　**—** 不由该开关决定（通常意味着任何取值下都可用）

| 功能点 | `engine: local` | `engine: remote` | `cloud: on` | `llm: light` | `llm: heavy` |
| --- | --- | --- | --- | --- | --- |
| 棋盘 / 走子 / 规则判定 | — | — | — | — | — |
| 演示线生成与播放 | — | — | — | — | — |
| PGN 导入 / 导出 | — | — | — | — | — |
| 战术题判定 + 正解播放 | — | — | — | — | — |
| 棋风（评估权重调参） | — | — | — | — | — |
| 三条最佳路线（MultiPV=3） | ◐ 业余棋力 | ● | — | — | — |
| 逐手评分找漏招 | ◐ 会误判重点 | ● | — | — | — |
| AI 对手棋力 | ◐ 偏弱 | ● | — | — | — |
| 局面点评（信号触发） | — | — | — | ● | ● |
| 多轮追问 / 指棋盘讲解 | — | — | — | ◐ 轮次受限 | ● |
| 每步点评（chess_tutor 模式） | — | — | — | ○ 不做 | ◐ 可做但不建议 |
| 复盘 · 赛后报告 | ◐ 找不到重点 | ● | ● 存历史报告需要 | ● | ● |
| 跨设备存档 / 断点续练 | — | — | ● | — | — |
| 题库下发与更新 | — | — | ● | — | — |
| 错题记忆 / 用户画像（阶段三） | — | — | ● | ● | ● |

### 3.1 从矩阵里读出的四条结论

1. **上面五行（棋盘 / 演示线 / PGN / 战术题判定 / 棋风）全 `—`**，意味着它们是产品的底座，
   与任何开关无关。**三个开关全 off 时，产品仍然是一个完整可用的工具**，
   缺的只是"语言"。界面不许空，要显示"功能都在，只是不讲话"。
2. **有两个功能点是「一直琥珀」的**：逐手评分找漏招、AI 对手棋力。它们**只看 `engine`**——
   `llm` 开到 heavy 救不了，`cloud` 开了也救不了。这是唯一一处"加功能会被误以为能修复"的地方。
3. **`cloud: on` 买的是连续性，不是能力。** 跨设备存档、题库下发、画像不丢。
   阶段三的记忆层 = `cloud on` + `llm`（两者都需要）。
4. **「每步点评」在 `light` 下是 ○**：不是做不到，是**不做**。它把 3~15 秒的等待塞进每一步之间，
   还会把真正该讲的关键手淹没在例行公事里——这正是 chess_tutor 最该避免的做法。

### 3.2 各子系统的最低开关组合

| 子系统 | 最低可跑 | 缺了会怎样 |
| --- | --- | --- |
| 沙盘分析 | 全 off 即可用；`llm: light` 才会"说话" | 无 LLM 时是个安静的工具：能看能走，没人讲解 |
| 战术闯关 | 全 off 即可用；`cloud: on` 才有大题库与打卡同步 | 无云时是小题库刷题器，几十题后没有新鲜感 |
| 棋局复盘 | `engine: remote` + `llm: light` | 无远程引擎时报告会说错重点（漏招识别不准） |
| 陪练对弈 | 全 off 能下（棋力弱）；`llm: light` 才有意义 | 无讲解时就是个不会说话的弱对手，价值有限 |

## 4. 三条铁律

1. **走子、判定、评分、演示线全部在 `engine: local` 下完成。** 离线不是残废模式，
   缺的只是"语言"。离线时界面不许空。
2. **调 LLM 的开关不是「走了一步」，而是「出现了一个值得讲的信号」**：
   分数跳变超阈值 / 终局 / 用户主动提问 / 答错题目。触发后仍受预算约束（次数上限 + 冷却）。
3. **降级必须显形。** 提前在界面说明当前缺哪个能力、点了会怎样，
   不要等按钮点下去才报错。

## 5. `engine: remote` 的两条路径

`remote` 是后续升级项，**当前一律 `local`**，两条路径暂不展开实施：

| | 微信云托管容器（managed container） | 自建 VPS |
| --- | --- | --- |
| 域名备案 | 免（`callContainer` 走微信私有协议） | 需已备案 HTTPS 域名 + mp 后台配白名单 |
| 用户鉴权 | header 直出 `openid`，不碰 AppSecret | 自建 `code2session`，需保管 AppSecret |
| 冷启动 | 缩容到 0 后重启，实测 20~40 秒 | 常驻，无冷启动 |
| 算力 | 起步 0.25 核，对引擎偏弱 | 2 核起，可多线程、可并发 |
| 超时 | `CallContainer` ≤ 15s | `wx.request` ≤ 60s |
| 成本 | 缩到 0 约 2 元/月；常驻 0.25 核约 260 元/年 | 约 300~600 元/年（含域名，首年活动价不可持续） |
| 多端复用 | 绑定微信生态 | Web / H5 / App 可共用 |

其余硬约束：云托管仅支持 HTTP、不支持公网 IP 访问、容器无持久化存储、默认公网域名不可用于生产。

**共同的法务前提**：GPL 传染性来自「分发二进制」。两端都是仅在服务端运行、小程序只做 HTTP 调用，
因此都不触发开源义务。前提是**任何 GPL 代码都不进小程序包**——
将来若做 Web 版，也**不能把 wasm 版 Stockfish 打进前端**，那构成分发，GPL 立刻复活。

## 6. 接入点（现在就该预留的）

三件事，成本都很小，但决定了将来换实现时是否要动上层：

1. **探测结果落到页面状态。** 现有 `data.cloudReady` / `data.cloudHint`
   （见 AGENTS.md §8 的"先探测再降级"）扩成三个开关的探测结果，页面据此渲染。
   点评按钮在 `llm: off` 时**不置灰**，而是改成「离线中，可查看引擎分析」并说明原因。
2. **引擎调用收口在门面里。** `utils/ai-client.js` 本来就是分析门面，按 `engine` 开关选择实现，
   **保持 `analyze()` 契约不变**（AGENTS.md §4 的冻结要求）。
3. **并存 + 回落，不是替换。** `engine: remote` 失败或超时**必须自动回落 `local`**——
   「四条保底通道（规则判定 / 走法生成 / 演示线 / 本地评分）不依赖网络」是 AGENTS.md §8 的硬要求。
