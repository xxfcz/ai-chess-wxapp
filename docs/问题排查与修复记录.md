## 1. 预览报 `wx.createSelectorQuery is not a function`

**现象**：右侧预览面板一打开就报错，页面不可用。

**根因**：WorkBuddy 网页版预览的运行时**只实现了微信接口的一个子集**，不提供 `wx.createSelectorQuery`。
原方案用 `<canvas type="2d">` + `createSelectorQuery().select('#chessboard')` 取节点，
取不到就抛错，页面初始化直接中断。

**修复**：整块换掉 Canvas 方案。

- 删除 `utils/board-render.js`（Canvas 绘制层）。
- 新增 `utils/board-model.js`：纯函数，把棋局编译成 64 个格子的视图数据
  `{ sq, cls, glyph, color, mark, ct, cb }`；棋盘由 WXML 的 8×8 `view` 网格渲染，
  棋子是格内文字字形（实心 ♔♕♖♗♘♙），靠 `.piece-w` / `.piece-b` 颜色区分黑白。
- 新增 `utils/device.js`：窗口宽度与 Toast 的安全取值，
  按 `getWindowInfo → getSystemInfoSync → window.innerWidth → documentElement.clientWidth → 375`
  逐级降级，全部 `try/catch`，**永不抛错**。
- 拖拽落点不再依赖棋盘真实坐标：记下按下格与手指起点，
  用「位移 ÷ 格宽」四舍五入得到行列偏移，**无需查询 DOM**。
- `utils/geometry.js` 补 `squareToCell / cellToSquare / isLightSquare`，纯函数无 wx 依赖。

**复用要点**：**任何依赖 wx 接口的能力都要在应用内先探测再降级**，不要靠报错兜底。

## 2. （隐藏 bug）棋盘上下镜像 + 黑白互换

这条不是用户报的，是在改渲染层时发现并顺手修掉的 —— 但危害最大，因为它**在起始局面下完全看不出来**。

**根因**：`board-model.js` 从 chess.js 的 `board()` 取子时写成了 `board[rank]`，
而 `board()` 的**第 0 行是第 8 横线**，正确写法是 `board[7 - rank]`
（rank 为 0 基、a1 = 0）。错写会导致**整盘上下镜像 + 黑白互换**。

**为什么一直没暴露**：初始局面左右上下都对称，镜像后长得一模一样；
只有走到非对称局面（比如走了几步的中局）才会画错。

**修复**：改为 `board[7 - rank]`，并在 `analyze-page.test.js` 加了 5 条回归断言
（g2 黑王、e1 白王、h1 白车各自落对格，且镜像位置 g7 / e8 / h8 必须为空）。

## 3. 三条路线一行都不显示

**现象**：点「AI 分析」只显示「点击任一路线…」+「深度 3 · 15084 节点 · 249ms」，**三条路线一行都没有**。

**根因**：`analyze.wxml` 里路线循环把循环变量写进了 **`wx:for` 元素自身的属性**：

```html
<view wx:for="{{analysisLines}}" wx:key="rank"
      class="line {{hintIndex === index ? 'line-active' : ''}}"
      data-index="{{index}}" bindtap="onPreviewLine">
```

预览环境在渲染元素**自身**属性时取不到 `index` → 整行渲染不出来；
而同级、不依赖 `index` 的说明文字照常显示 —— 与现象完全吻合。

**对照验证**：棋盘 `wx:for="{{cells}}"` 的属性只引用 `item.*`，一直正常；
`moveRows` 也不引用 `index`。**全页只有路线循环引用了 `index`，也只有它渲染失败。**

**修复（约定）**：模板里不要在循环元素自身的属性中引用循环变量。

- 下标与高亮态**随数据下发**：`analyze.js#buildLineViews()` 给每条路线补
  `idx`（0 基下标）、`key`（字符串唯一键）、`active`（是否高亮）。
- 模板改为 `class="line {{item.active ? 'line-active' : ''}}" data-index="{{item.idx}}"`，
  `wx:key="key"`。
- 点击高亮改由 `applyLineActive(index)` **重建数组**，不用 `setData` 的路径语法
  （`'list[0].x'`）—— 兼容性更好。
- `moveRows` 的 `wx:key="no"`（数字）换成字符串键 `key`，一并消除数字键风险。
- 顺手去掉模板里的 `<block>`（预览支持范围未知），改成独立 `wx:if`。

**回归守卫**：`analyze-page.test.js` 第 13 节对以上三点做**静态检查**，
以后再把 `{{index}}` 写回 `wx:for` 元素自身属性会立刻变红。

## 4. 点评误报「模型服务暂时不可用」

**现象**：点「生成点评」显示「模型服务暂时不可用，请稍后再试。」，但云服务实测完全正常。

**根因有两层**：

1. **误报**：SDK 在底层请求失败时统一抛 `code` 以 `gateway_` 开头的错误
   （`gateway_network_error` / `gateway_stream_interrupted` / `gateway_invalid_response`），
   其中 `gateway_network_error` 表示「`wx.request` 失败/中断」。
   原来的 `describeLLMError()` 把整个 `gateway_*` 都翻成「模型服务暂时不可用」
   → **把环境限制误报成了云端故障**。
2. **真实故障**：预览环境的 `wx.request` **接受 `enableChunked: true`，
   但返回的任务对象上没有 `onChunkReceived`**。SDK 的流式实现是**无条件**调用
   `task.onChunkReceived(...)` 的，于是同步抛 `TypeError: task.onChunkReceived is not a function`，
   被包成 `gateway_network_error`。
   另外该 SDK **只支持流式** —— `create({stream: false})` 会抛 `request_stream_required`，
   所以不能靠「退回非流式」解决，只能自己补分块能力。

**修复**

- `utils/workbuddy-cloud-diagnostics.js`：wx 适配器新增**自适应分块降级**。
  先按原生分块发起；若任务对象没有 `onChunkReceived`，中止它，改用一次性普通请求
  （`responseType: 'text'`），把**整包响应体当成单个分片**，用自写的 `encodeUtf8()` 编成
  `ArrayBuffer` 推给 SDK 的 SSE 解析器。结论记进模块级状态，之后不再白发探测请求。
  同时补了分片/响应头缓冲（回调可能早于监听器注册）、看门狗超时、
  存储接口的防御性透传（环境缺 API 时返回 `''` 而不是抛错）。
  适配器暴露 `streamingStatus()`（`null` = 未探测 / `true` = 原生支持 / `false` = 已降级）。
- `utils/ai-client.js`：`describeLLMError()` 拆成 `llmErrorInfo(err)` → `{ message, detail, kind }`；
  `gateway_network_error` 改报「网络受限」并说明端上分析不受影响，
  只有真非网络类 `gateway_*` 与 `model_*` 才报「模型服务暂时不可用」。
  `detail` 汇总错误码 + 逐层 `cause.message`，界面用小字等宽行显示便于定位。
- `pages/analyze/*`：新增 `coachDetail`（排查线索行）与 `commentingHint`（等待说明）。

**实网验证**（`.workbuddy/tests/cloud-live-probe.js`，需网络、耗少量额度）：
真实云服务 + 「像预览一样不给分块回调」的 wx → 拿到 192 个分片 / 约 24s 的真实中文点评，
`streamingStatus() === false` → 功能可用（只是失去逐字效果，一次性显示）。

## 5. 点评报 `request:fail abort`

**现象**：`gateway_network_error · wx.request (chunked) failed: request:fail abort`

**根因（上一轮自己引入的）**：适配器发现环境不给 `onChunkReceived` 后会
`probe.abort()` 掉探测请求再改走一次性请求。但**真实环境里 `abort()` 会回调
`fail({ errMsg: 'request:fail abort' })`** —— 这个由我们自己制造出来的 fail
**抢先把整单判负**，`settle()` 的守卫于是把降级请求稍后拿到的正文直接丢掉。
**正文其实已经取到了，界面却报网络失败。**

**为什么上一轮没测出来**：假 wx 的 `abort()` 只置了一个标志位、**不回调 fail**。
**教训：打桩必须还原真实环境行为**，否则测试「绿着通过」而真环境照样报错。

**修复**

- 模块状态增加 `owner`（谁结算的）与 `abandoned`（探测请求是否已被主动放弃）；
- `settle(owner, isFail, result)` 记录 owner；
- 新增 `abandonProbe(probe)`：置 `abandoned = true` → abort →
  **若探测请求在放弃前已同步结算过，把 `finished` / `owner` 复位**，让降级请求仍能结算；
- 探测请求的 `success` / `fail` 一进来先判 `state.abandoned`，是则直接 return；
- `chunkedSupported === false` 时直接走降级，不再白发一次探测请求。

**回归守卫**：`cloud-adapter.test.js` 第 3b 节「中止探测请求本身触发 fail 时，
降级结果不能被丢弃」，且假 wx 的 `abort()` 已改成**会回调 fail**的真实行为。

## 6. 点评报 `request:fail timeout（云服务响应超时）`

**现象**：点「生成点评」等了几十秒后失败，错误行是
`gateway_network_error · wx.request (chunked) failed: request:fail timeout（云服务响应超时）`。

**复现**：写了 `cloud-model-probe.js`（用应用**真实的**教练提示词跑真实云服务），
本机一模一样复现：`durationMs: 50006` —— 是**适配器自己的 50 秒兜底看门狗先开火**。
（括号里的中文就是我们自己写的，说明是时限问题，不是环境问题。
上一轮的实网探针提示词很短、只跑了 29s，所以没暴露。）

**根因（用 `cloud-model-bench.js` 量出来的）**：`auto` 路由到的是**思考型**模型 `hy4-preview-f`：

| 模型 | 耗时 | 正文 |
|---|---|---|
| `auto` → `hy4-preview-f` | **> 50 s** | `max_tokens=360` 时预算被思考吃光，**0 字** |
| `deepseek-v4-flash` | **2905 ms** | 242 字 |
| `hunyuan-chat` | **4980 ms** | 143 字 |
| `glm-5.3-flash` | **10647 ms** | 234 字 |

一个三五句话的点评，用思考型模型既慢又浪费额度。

**修复**

1. 模型选择规则改为 `MODEL_PREFERENCE = ['deepseek-v4-flash', 'hunyuan-chat', 'glm-5.3-flash']`，
   其后才 `auto` / `default` / 第一条可用；跑通的模型缓存并排首位。
2. 请求加 `max_tokens: 480`；系统提示词补「150 字以内」。
3. **失败自动换模型重试一次**（`shouldTryNextModel`）：只重试 `timeout` / 空正文 / `model_*`；
   链路类、鉴权、额度、参数错误**不重试**（换模型救不了，只会多等一倍、多烧额度）；
   用户取消（`signal.aborted`）绝不重试。
4. **超时与「网络不通」分开报**：`kind: 'timeout'`，判定条件是
   「`code` 以 `gateway_` 开头 **且** `detail` 含 `timeout`」，文案
   「云端模型这次没有在限时内返回…可以再点一次」。
5. 适配器时限重定：一次性请求兜底 **75 s**、`wx.request` 自身 `timeout = 80 s`
   （略大于兜底，让可读文案先生效）；分块流式改为**空闲看门狗 25 s / 每收到分片就重置**，
   不再用「从开始固定 45 s」。自检要缩时限时走 `createDiagnosticWx(wx, overrides)` 第二参。
6. `app.json` 加 `networkTimeout.request = 90000` 再兜一层。
7. 交互：生成中再点一次 = **取消**（`cancelCoach()`，`_coachCancelled` 守卫，
   取消不报错、可立即重来）；等待提示每秒刷新「已等待 N 秒（模型名）」。

**实网复测**：`cloud-model-probe.js` → **2396 ms**、125 字真实中文点评、
实际服务模型 `Deepseek-V4-Flash（DeepSeek）`、请求明细 `completions: 2202 ms`。

## 7. 真机报 `TextDecoder is not defined`

**现象**：预览一切正常，**真机**上点「生成点评」报 `TextDecoder is not defined`。

**根因**：云服务 SDK 的 SSE 解析器内部写死了 `new TextDecoder('utf-8')`（**全局对象**），
并且是 `decode(bytes, { stream: true })` 的**增量**用法。
浏览器 / Node 运行时都有这个全局对象 → **网页版预览一直正常**；
**微信小程序运行时没有 `TextDecoder`** → 原生分块的**第一个分片到达就抛错**。

这是「预览绿、真机红」的典型：**只看预览永远发现不了**。

**修复**：新增 `utils/text-codec.js`。

- `installTextCodec(scope?)` —— **只在缺失时安装，绝不覆盖宿主已有实现**；
  返回 `{ installed, decoder, encoder, target }` 便于自检与界面提示。
- `Utf8TextDecoder` 支持 `new TextDecoder('utf-8')` / `decode(bytes)` /
  `decode(bytes, { stream: true })`（**跨调用保留被截断的多字节序列**）/ `decode()` 收尾；
  非法字节给 `U+FFFD` 而不抛错；`Utf8TextEncoder` 一并补上。
- 安装点**两处**：`app.js` 启动时 + `utils/cloud.js` 顶部副作用 `require`
  （保证只要碰云服务就一定先补好）。

**为什么增量语义必须实现**：SDK 是按行解码的，一个 UTF-8 中文字符经常被切在
两次 `decode()` 调用之间，如果不保存残留字节，就会偶发吐出 `�`。

**验证**：新增 `cloud-realdevice-probe.js`（真机形态探针）——
wx 原生分块**可用**（任务对象有 `onChunkReceived`、边收边回调、`chunk.data` 是 `ArrayBuffer`）、
`abort()` 会回调 fail、并**把 `global.TextDecoder` 删掉**，再跑真实云服务：

```
补装成功 → 97 个原生分片 → 增量回调 6 次 → 首个增量 1249 ms
→ 144 字真实中文点评 → 总耗时 2179 ms → 实际服务模型 Deepseek-V4-Flash（DeepSeek）
```

## 9. 搭建期踩的坑（同样可复用）

### 9.1 `validate_fen()` 只校验不载入

`chess.js@0.10.3` 的 `validate_fen()` **只校验不载入**，必须显式 `load(fen)`，
否则棋盘永远是初始局面。

### 9.2 `moves({verbose:true})` 让搜索慢 13 倍

`chess.js` 的 `moves({ verbose: true })` 会为每个走法生成 SAN
（`move_to_san` 内部还会再遍历一次做消歧），接近 **O(n²)**。
直接拿它做 Alpha-Beta，开局深度 3 要 **3 秒**。
在 `utils/chess.js` 末尾加了本地扩展 `raw_moves / raw_move / raw_undo / raw_board`
（暴露内部 0x88 棋盘），搜索树内部全走 raw 路径、只在根节点生成一次 SAN
→ **降到 230 ms（13×）**。

### 9.3 `_switchTurn()` 替换 chess 实例

`Game.tryMove()` 里 `_switchTurn()` 会替换 `this._chess` 实例；
若先把实例存进局部变量，翻转后就操作到旧实例上了（自由模拟走子永远失败）。

### 9.4 自由模拟的合法落点要在副本上算

「自由模拟双方」（拖对方棋子自动翻转行棋方）的合法落点必须在**副本**上翻转行棋方再算，
否则拖动对方棋子时高亮为空、永远走不动。

### 9.5 分析进行中点点评会误报

分析进行中点「生成点评」曾误报「请先完成局面分析」；
改成 `runAnalyze()` 返回可 `await` 的 Promise + `ensureAnalysis(fen)` 轮询兜底。

## 10. 沉淀下来的可复用规则

### 10.1 环境能力
1. **预览环境只实现了 wx 的一个子集**，且清单无法从本地静态分析确认
   （预览模拟器是远端服务，本地 `app.asar` 里没有它的垫片）。
   因此**任何依赖 wx 接口的能力都要应用内探测 + 明确降级文案**。
2. 已确认缺失/行为差异：无 `createSelectorQuery`；
   `wx.request` 接受 `enableChunked` 但任务对象无 `onChunkReceived`；
   `abort()` 会回调 `fail`；触摸拖拽可能退化成鼠标事件（所以**必须同时提供点选路径**）。
3. **反向也成立**：`TextDecoder` 这类**全局对象**在预览里有、在真机没有 —— 只看预览发现不了。

### 10.2 WXML 模板硬约束
1. 不要在 `wx:for` 元素**自身的属性**里引用循环变量 `index`
   （正文子节点里可以）；做法是把下标写进数据。
2. `wx:key` 用**字符串字段**，不要用数字字段。
3. 不用 `<block>`，用独立的 `wx:if`。
4. 高亮/选中类状态**随数据下发**更稳，不要依赖 `setData` 的路径语法。

### 10.3 云服务
1. 模型要**按「够快」挑，不要默认 `auto`**（`auto` 会路由到思考型模型）。
2. **响应分片的 `chunk.model` 才是真正服务的模型**，把它显示到界面上，别让用户猜。
3. **超时 ≠ 模型故障 ≠ 网络不通**，三者文案必须分开。
4. 失败重试只对「换模型救得了」的错误（超时 / 空正文 / `model_*`）；
   链路类、鉴权、额度、参数错误不重试；用户取消后绝不偷偷再发。
5. **真机才校验 request 合法域名白名单**：`wx.request` 目标 `https://mp-api.app.workbuddy.host`
   必须在**微信公众平台 → 开发 → 开发管理 → 开发设置 → 服务器域名 → request 合法域名**登记，
   否则真机报 `url not in domain list`。开发者工具因 `project.config.json` 的 `urlCheck:false`
   跳过校验，所以**预览绿、真机红**。「导入时只能选不使用云服务」与此无关
   （那是 CloudBase 绑定，本 SDK 走普通 `wx.request`，是两回事）；但该现象往往意味着用的是
   **测试号**——测试号配不了服务器域名，真机必然失败，需改用已注册的正式 AppID 再加白名单。
6. **`wbapp_...` 是 WorkBuddy 发布平台的内部应用 id，不是微信 AppID，永远不要写进 `project.config.json`**。
   微信 AppID 一律以 `wx` 开头。若把它填进 `project.config.json` 的 `appid`，
   开发者工具会因找不到对应微信小程序而报「登录用户不是该小程序的开发者」，预览与真机调试同时失效。
   该 id 只在 WorkBuddy 发布流程里使用（其受管小程序的域名白名单已含 `mp-api.app.workbuddy.host`）。
7. **`.wbapp_<id>.genie` 是发布登记标记文件**（记录 `appId/name/localDir/appType`），由发布工具生成在
   项目根目录。它不是微信配置、开发者工具一般不读；但若怀疑它干扰真机调试信道（曾出现 `-50005 连接断开`），
   可临时移出项目根（如挪到 `.workbuddy/_genie_backup/`），需要发布时再放回。本地开发与真机调试阶段，
   项目根目录应保持 `project.config.json` 的 `appid = wx...` 测试号 + 无 `.genie` 文件。

### 10.4 测试方法
1. **打桩必须还原真实环境行为**（尤其 `abort()` 会回调 `fail` 这类副作用），
   否则测试绿着通过而真环境照样报错。
2. 分层次验证：**静态守卫**（模板约束）→ **单元用例**（逻辑分支）→
   **实网探针**（预览式 / 真机式两种形态，需网络、耗额度，不进常规回归）。
3. 时间类硬性断言在繁忙机器上会误报 —— 放宽为「防性能回归」阈值。
