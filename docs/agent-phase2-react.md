# 阶段二 · Reason-Act Loop（多轮 ReAct）

> 让 Tutor 具备自主循环：用户提问后，Agent 自己决定要查什么、查几次，再组织答复。
> 总纲见 `docs/agent-plan.md`，阶段一见 `docs/agent-phase1-tutor.md`。
>
> 本篇**刻意不写函数级改造清单**——阶段一的工具层尚未落地，现在把实现细节定死，
> 等到开工时大概率推倒重来。这里只冻结**契约、预算模型与验收口径**。

---

## 1. 目标

阶段一之后，模型获得了「引用端上生成的合法走法」的能力，但它仍是**一次往返**：
看一眼 prompt 里那三条线，然后组织语言。

阶段二要给它的是：

> **当它没有足够依据时，自己去查。**

最典型的用户诉求是「为什么」型提问——这类问题的答案无法靠读 prompt 得出，必须真的去看某步之后会发生什么：

- 为什么这里不能 Nc3？（要看 Nc3 之后黑方的最佳反击）
- 为什么引擎说 Qxd5 好，我吃兵不是更直接吗？（要比较两条线的最终结局）
- 我被将杀了，但我就没看见那一步将军，它从哪来的？（要回溯攻击路径）

这些今天全部答不了，因为**模型没有 ACT 的能力**——它只能复述已经摆在面前的结论。

## 2. 产品设计

### 2.1 交互形态

新增「追问」入口，与首次点评并列：

```
[生成点评]        ← 阶段一的单次往返，仍在
[追问] [输入框]   ← 阶段二新增：针对当前局面继续提问
```

- 追问是**短会话**：一次提问触发一个完整的 ReAct 循环，产生一次答复；用户可以接着再问。
- 会话锚定在当前局面：**走子后旧会话自动归档**（否则对不上形势）。
- 用户界面需要可见的过程反馈（AGENTS.md §6.4 的模板约束前提下实现，见 §5.3）：
  ```
  正在验算第 2 步：Nc3 之后黑方的应对…
  ```

### 2.2 用户感知的取舍

| 收益 | 代价 |
|---|---|
| 能回答「为什么」 | 单次应答从 3~10s 上升到可能 15~30s |
| 答复有据可查（引用了她具体哪一局的验算） | 需要过程可见，否则用户以为卡住 |
| 同一局面可多次追问，逐步深入 | 需要会话预算，防止无限循环 |

**产品上的关键判断**：宁可让它慢一点但答得对，也不要快但答错。
棋类教学的容错率很低——一个错误的「为什么」比没有回答更有害，因为用户会记住它。

## 3. 需求说明

| # | 需求 | 验收方式 |
|---|---|---|
| **R1** | Agent 能在一次提问中**自主决定**调用哪些工具、调用几次 | 场景集：至少覆盖「比较两手」「解释为何某手劣」「找攻击来源」三类 |
| **R2** | 工具调用受**硬预算**约束，绝不失控 | 单测：构造诱导性提问，断言调用次数/节点数/时长均不超上限 |
| **R3** | 任一步失败不导致整轮失败 | 单测：工具抛错、LLM 超时分别注入，验证降级路径 |
| **R4** | 四条保底通道在网络不可用时**依然可用** | AGENTS.md §8。无网络时工具层照常工作 |
| **R5** | 用户可随时中止，且中止后**不再产生任何新的请求** | 单测：`signal.aborted` 后无后续网络调用 |
| **R6** | 过程对用户可见 | 界面显示当前验算步骤；不少于一次中间态更新 |
| **R7** | 走子后旧会话自动失效，不拿旧结论套新局面 | 单测：走子后再追问，不出现跨局面的引用 |
| **R8** | 单次会话**锁定同一个模型** | 现有 `cachedModelId` 复用；单测断言不重复探测模型 |
| **R9** | 工具结果**压缩后**才回传 LLM | 静态检查：不得出现完整 FEN 数组/PV 全量回传 |
| **R10** | 三套既有回归 + 阶段一测试仍全绿 | 门禁命令见总纲 §7.1 |

## 4. 系统设计

### 4.1 循环结构

```
用户提问 q，局面 F
      │
      ▼
┌─ loop ────────────────────────────────────────────┐
│  构造 messages = [system, Few-shot, history, q, F]  │
│                                                    │
│  ① LLM 产出一步思考 or 一个工具调用请求              │
│  ② 若为工具调用 → 端上执行（零耗时）                  │
│     结果压缩 → 追加进 messages                      │
│  ③ 预算检查：超限 → 强制进入总结                     │
│  ④ 回到 ①                                          │
└────────────────────┬───────────────────────────────┘
                     │ LLM 给出 final 答复
                     ▼
              渲染（含引用到的验算步骤）
```

### 4.2 工具注册表

阶段二在阶段一的三个工具之上，增加面向「为什么」的专项能力：

| 工具 | 输入 | 用途 | 备注 |
|---|---|---|---|
| `analyze` | fen, depth | 重新评估局面 | 复用现有 `analyzePosition` |
| `legal_moves` | fen, sq | 某子能去哪 | 阶段一已有 |
| `expand_line` | fen, moves | 看指定序列之后的发展 | 阶段一已有；**回答「为什么」的主力** |
| `describe` | fen | 局面结构化特征 | 阶段一已有 |
| `compare_moves` | fen, moves[] | **比较若干候选的最终结局** | 新增，本质是 `expand_line` 的批处理 |
| `why_bad` | fen, move | **解释某手为何差**：best vs 该手的分差 + 关键差异抓住 | 新增，组合型工具 |

> `why_bad` 这类「组合工具」值得投资：让模型一次调用拿到结构化的因果，
> 好过让它自己拼三轮 `expand_line` 再推理——既省往返，也省 token。

### 4.3 预算模型（阶段二的核心约束）

**这是本阶段最需要提前定死的部分**，因为它决定了产品能否用，而不是代码怎么写。

因为工具在端上、几乎零耗时，瓶颈完全在网络 RTT 与端上搜索自身。所以预算要分三个维度：

| 维度 | 建议上限 | 理由 |
|---|---|---|
| **轮次（往返次数）** | 3 次 | 每次 3~10s，超过 3 次用户必然以为卡住 |
| **工具调用总次数** | 8 次 | 端上 JS 引擎在手机上 junior 体量有限，别把自己拖死 |
| **搜索节点总量** | 待实测标定 | 沿用 `engine.analyze` 的现有指标；首次集成时测出基线 |
| **整轮墙钟时间** | 30s 硬上限 | 到点在**最后一次已完成的工具结果上**强制总结，不留半截答案 |

三条实现纪律：

1. **按整轮分配一次性请求的超时预算，而不是每次请求独立叠乘。**
   参考：`cloud-adapter` 现有 `PLAIN_CEILING_MS = 75s` / `CHUNK_IDLE_MS = 25s`，
   若三轮各自独立套用，最坏情况会远超 30s 的目标。
   正确做法是把这些上限作为**整轮共享额度**，用完即止。
2. **预算耗尽时必须有优雅降级**：用已获得的工具结果生成「我能确认到这一层」的答复，
   而不是抛错。半截但有据的答案，胜过一句"服务超时"。
3. **用户输入新的提问后，上一轮的预算不清零累计到下一轮**——预算是**每个会话**的，
   否则用户可以通过连续追问无限累积。

### 4.4 失败分级（区别于阶段一的单次重试）

现有的 `ai-client#shouldTryNextModel(err, signal)` 已导出，它的粒度是**单次请求**。
阶段二需要把它上提到**会话层**：

| 失败层级 | 含义 | 处理 |
|---|---|---|
| 工具失败 | 端上异常（几乎不会发生） | 记日志、跳过该工具，继续循环 |
| 单步 LLM 失败 | 这一轮的生成失败 | **换模型重试这一步**；不重置整个会话 |
| 会话失败 | 多轮连续失败 / 预算耗尽 | 结束会话，给出可读说明，**不重试** |
| 链路失败 | `gateway_network_error` 等 | 立即结束，**不重试**（AGENTS.md §7 已定：这不换模型解决不了问题） |

> 用户取消必须位于最高优先级：任何时候 `signal.aborted` 为真，**不得再发起任何请求**。
> 现有 `shouldTryNextModel` 已处理了这一条，阶段二要把它贯彻到每一层。

## 5. 契约

### 5.1 工具调用的消息格式

LLM 侧的工具请求建议采用**紧凑 JSON**（而非函数调用元数据），原因见 §6 待决策项 Q2：

```json
{"think":"需要比较 Nc3 和 Nd2 的差别",
 "act":{"tool":"compare_moves","fen":"<当前 FEN>","moves":["Nc3","Nd2"],"depth":3}}
```

工具结果回传格式（**压缩后**）：

```json
{"tool":"compare_moves","ok":true,
 "result":[{"move":"Nc3","cpDiff":-120,"key":"Nc3 后被 Qb6 打双","verdict":"劣"},
           {"move":"Nd2","cpDiff":0,"key":"保持结构完整","verdict":"佳"}]}
```

### 5.2 会话状态

```js
{
  sessionId: string,        // 一次对话
  fen: string,              // 锚定局面；走子即失效
  budget: { turnsLeft, callsLeft, nodesLeft, deadlineAt },
  messages: [...],          // 含工具调用与压缩结果
  modelLocked: string|null, // 本会话锁定的模型
  phase: 'thinking'|'acting'|'summarizing'|'done'|'aborted'
}
```

### 5.3 UI 契约补充

AGENTS.md §6.4 规定 `wx:for` 元素**自身属性不得引用循环变量 `index`**，
因此对话流、工具步骤这类列表必须：

- 每条消息自带 `key`（字符串）、`idx`、`role` 等字段，由数据层下发；
- 不使用 `<block>`；
- 过程态（「正在验算第 N 步」）走单一字段更新，不依赖模板内的路径语法。

## 7. 验收

### 7.1 场景集（每一条都需要人工过一遍）

| 提问 | 期望行为 |
|---|---|
| 「为什么这里不能 Nc3？」 | 至少 1 次 `expand_line`，答复含具体反击手 |
| 「Qxd5 和 Nf3 哪个好？」 | `compare_moves`，给出分差与关键差异 |
| 「我怎么就被将死了？」 | 回溯攻击路径，指出被忽略的那一步 |
| 「随便讲讲」（无明确意图） | **不触发**工具循环，直接点评（省时间） |
| 追问中局面改变（用户走了子） | 旧会话作废，明确提示 |
| 中途取消 | 无后续请求，状态干净 |

### 7.2 必须守住的红线

- 任一工具抛错 → **不许**把异常栈显示给用户，也不许整轮崩掉；
- 用户取消后 → **必须零**新请求（`CHECK`：用打桩 wx 断言调用次数）；
- 无网络 → 工具层照常工作，仅 LLM 侧给出 `env_no_network` 文案。

## 8. 风险

| 风险 | 影响 | 提前预防 |
|---|---|---|
| **端上搜索被自己拖死** | 手机卡顿、发热、ANR | 硬预算（§4.3）；首次集成时实测标定节点上限 |
| 无限循环 / 反复验算同一手 | 时间耗尽、体验崩坏 | 轮次上限 + 重复调用检测（同参数第二次直接复用结果） |
| 过程不可见导致「以为死了」 | 用户中途离开 | R6 强制过程反馈；转圈超过 5s 必须有文字 |
| Agent 自信地给出错误因果 | **比答不出来更有害** | 答复必须引用工具结果；不允许脱离验算下结论 |
| 网关是否透传 tools 未知 | 可能白写一层 | Q2 建议先探针再动手 |
| 30 秒仍答不完 | 用户流失 | 预算耗尽时的优雅降级（§4.3 纪律 2） |
