# 产品重构方案：棋局能力平台 + 扩展模块

> 重构日期：2026-10-21
> 背景：远端 Stockfish 已在真机跑通（`https://chess.imex.de5.net/`）；现有 `pages/analyze` 已实现
> FEN → 棋盘 → 3 线引擎分析 → AI 点评，并在 AI 点评中具备**走法分支 + 点击链接走子/定位**的差异化能力。
> 参考：`chess_tutor` 的「多入口但共用同一核心（ChessGame + 引擎 + LLM 教练）」简洁界面（`docs/黑白格大师_vs_chess_tutor_选型分析.md`）。
> 方法论：Superpowers（先想清楚规格，再写计划，TDD，系统收尾）。

---

## 0. 一句话结论

把「棋局会话（FEN/PGN + 走子树 + 引擎分析 + AI 点评）」抽成**无 UI 的纯功能平台层（L0）**，其上是一组**共享 UI 组件层（L1）**，最上是**模式配置层（L2：对弈 / 分析 / 打谱 / 练习）**。导航采用 **Landing 首页（主包）+ 各模式分包页面**：首页卡片入口 → 各自模式的独立分包 page（加模块 = 加一个分包 page + 在 Landing 注册一张卡片）。现有「走法分支 + 点击定位」的差异化能力上升为**平台级一等公民（comment-model）**，被所有模式复用。

---

## 1. 产品形态：Landing 首页（主包）+ 各模式分包页面（推荐）

借鉴 `chess_tutor` 的「多入口共用同一核心」，在微信小程序里落地为 **Landing 首页（主包单页）+ 各工作模式独立分包页面**。

> **关于「多页面 vs SPA」的澄清（第二轮决策，2026-10-21）：**
> - 微信小程序**没有「HTML 页面」概念**；用户说的「多入口 HTML 页面」在小程序里等价于「每个模式一个 `pages/` 下的 page（wxml/wxss/js）」。`chess_tutor` 是 Next.js 才有 HTML 路由，小程序不是。
> - **多 page 跳转不会增大主包体积**：包体积由构建时的代码文件大小决定，与运行时是否重建组件无关。用**分包（subPackage）**即可——主包只含 `app` + 共享基础库（`session` / `engine-service` / `analysis-service` / `coach-service` + `BoardView` 等 L1 组件），各模式是独立分包 page，构建时共享模块去重，不重复打包。
> - **「重建」的运行时成本可控**：把当前 session 与「已分析节点」缓存进**全局 store**（`app.globalData` 或自写单例），跨 page 保留；远程引擎本就无状态、本地引擎是纯函数调用，都不必保活长生命周期实例。重新进入 page 只重渲 UI，不会重算已分析过的局面。

架构：

```
┌─────────────────────────────────────────────┐
│  Landing 页（主包）                           │
│   四张入口卡片 + 设置入口 + 剪贴板自动导入      │
│   [ 开新局 ] [ 分析棋局 ] [ 打谱 ] [ 学习 ]    │
└─────────────────────────────────────────────┘
            │ 选卡片 → 配 session 模式 → navigateTo 分包 page
            ▼
┌─────────────────────────────────────────────┐
│  模式 page（各自分包）                         │
│   对弈 / 分析 / 打谱 / 练习                     │
│   只放「该模式薄逻辑 + 配置」，棋盘/引擎/点评    │
│   全部引用主包共享库与 L1 组件                   │
└─────────────────────────────────────────────┘
        ↑ 返回 Landing / 切模式 → 全局 store 保留 session
```

- **Landing（主包）**：四张入口卡片 + 设置 + 剪贴板自动导入。只负责「选模式 + 初始化 session + 读取设置」，不含棋盘逻辑。
- **模式 page（分包）**：各自只放「该模式的薄逻辑 + 配置」，棋盘/引擎/点评全部引用主包共享库与 L1 组件，互不重复打包。
- **为什么不用 tabBar**：最多 5 个、会与模式内子 Tab 冲突、小屏拥挤。
- **SPA 单页双视图仍可选**：若你要「切换零重载、棋盘/引擎完全不重建」，可改回单 page 内切视图（代价：4 个模式逻辑挤在一个 page，主包需谨慎分包/懒加载）。本方案**默认推荐「分包多页」**，最贴合「加模块 = 加一个分包 page + 在 Landing 注册一张卡片」的扩展模型。
- **与现有结构关系**：现有 `pages/analyze` 单页 → 拆为 `Landing(主包)` + `analyze` 分包 page（分析模式）；对弈/打谱/练习各新增一个分包 page。

## 2. 平台分层（核心）

严格按「先无 UI 纯功能层，再 UI 组件层」落地。L0 是头，L1 是脸，L2 是不同妆造。

### 2.1 L0 · 纯功能模块层（headless，无 UI、可纯 Node 测）

| 模块 | 职责 | 现状 / 来源 |
|---|---|---|
| `session`（棋局会话模型） | 核心数据结构：root FEN + **走子树**（每个节点含 FEN、UCI、SAN、parent、children/variations、引擎分析、AI 点评）。操作：`applyMove / gotoNode / addVariation / deleteVariation / forkFrom / loadPgn / toPgn`。**内部一律 FEN+UCI**（遵循现有数据格式约定），PGN 仅在 import/export 边界转换。 | **新增**（现有 `game.js` 是线性状态，需升级为树） |
| `engine-service` | 封装 `engine.js`（端上）+ `remote-engine.js`（云端），输出已冻结的 `analyze({fen,depth,multiPV})` 契约（含 source/degradedFrom/熔断）。 | 已有，收口复用 |
| `analysis-service` | 基于引擎的 3 线 MultiPV 分析 + 行棋方/白方视角换算 + 优劣标注；扩展到**节点级**（走子树每个节点可缓存分析）。 | 已有（`ai-client.formatScore` 等），抽服务 |
| `coach-service`（AI 点评） | 封装 `ai-client.js` + 云服务流式 LLM；产出**结构化点评**（文本 + 走法分支 + 可点走法 link token）。即差异化能力。 | 已有（`coach-demo.js` / `ai-client`），抽服务 |
| `comment-model` | 点评文本 → token 流：`text` / `moveLink(FEN 或 UCI 定位)` / `branch`。UI 据此渲染可点链接；点击 → `session.gotoNode(对应局面)`。这是「Tutor 必须能指棋盘」的**协议层**。 | **新增**（解析 + 渲染契约，现状散落在 analyze 页） |
| `tactic` / `opening` | 战术识别（牵制/击双/串击…）+ 开局库查询。纯逻辑，纯数据驱动，后期接。 | 后期（练习模块用） |

> 约定延续（见 working memory）：角色命名 教练=`tutor`、陪练=`sparrer`；既有 `coach` 标识符不动。规则判定=事实、引擎评分=意见，界面分层表达。

### 2.1b 三个服务与「3 线 MultiPV / AI 点评」的职责边界（第二轮澄清）

职责在**数据流上是清晰的**，但当前**代码里尚未完全拆墙**：

- **「基于引擎的 3 线 MultiPV 分析」= `engine-service` + `analysis-service`（两个服务，不是一）**：
  - `engine-service`（`engine.js` 端上 + `remote-engine.js` 云端，经 `ai-client.analyzePosition` 收口）只负责**算**——问引擎要 N 条原始路线（`lines[]`），它并不知道「3 线」这个业务语义。边界已独立、干净。
  - `analysis-service`（当前是 `ai-client.js` 里的 `formatScore` / `buildLineView` / `evalPercent` 一组函数）负责**读**——把 N 条原始路线整理成「3 线 + 行棋方/白方视角换算 + 评估条百分比 + 优劣 tone」，并支持**节点级缓存**（走子树每个节点缓存分析结果）。它目前**没有独立成模块**，而是和 coach 逻辑同处 `ai-client.js`。
- **「基于 AI 的点评」= `coach-service`（一个服务）**：当前 = `ai-client.js` 的 `requestCoachComment` + `coach-demo.js` 的解析/落地。它**消费** `analysis-service` 的结构化输出（FEN + 3 线）作输入，调 LLM，产出可点点评（含走法分支）。

**依赖链（已清晰）**：`engine-service`（算原始 N 线）→ `analysis-service`（读成 3 线 + 评分）→ `coach-service`（吃 3 线 + 局面 → 点评）。本次重构 L0 的物理动作 = 把 `analysis-service` 与 `coach-service` 从 `ai-client.js` 拆成各自独立模块，使三层边界在代码里也成立、可单测。

### 2.2 L1 · 共享 UI 组件层

| 组件 | 说明 | 来源 |
|---|---|---|
| `BoardView` | 复用现有 view 网格棋盘（`board-model` + `geometry`），支持 **focus 高亮**（Tutor 指棋盘）。 | 迁移自 analyze 页棋盘资产 |
| `EnginePanel` | 3 线分析 + 深度选择 + 来源标注（local / remote / degraded）。 | 迁移自 analyze 页 |
| `CommentCard` | 渲染 `comment-model` 的 token 流；`moveLink` 可点 → 触发走子/定位 + 高亮。 | **新增**（承载差异化） |
| `MoveTree` / `MoveList` | 走法树 / 谱浏览 + 分支折叠；点击节点定位棋盘。 | 新增（来自 session 走子树） |
| `SessionBar` | 单行状态条（优势数值 + 来源 + 模式标识）。 | 迁移自现有状态条 |

> 现有 `analyze-page.test.js` 的 WXML 静态守卫（循环变量/`wx:key`/不用 `<block>`）在拆组件时**必须继续遵守**。

### 2.3 L2 · 模式配置层（薄）

每个模式 = 对 Workspace 的一份**配置**（初始 session 来源、谁走子、是否自动分析、是否出着、点评触发时机、可见子区）。不重复实现棋盘/引擎/点评。

| 模式 | 初始来源 | 行棋方 | 自动分析 | 出着 | 点评触发 | 对应 chess_tutor |
|---|---|---|---|---|---|---|
| **对弈（人机）** | 空局 / 指定 FEN | 玩家 vs `sparrer`（陪练） | 每步后 | 引擎出着 | 自动（受 `autoCoach` + 对弈子策略 `playCoachScope`：`allSteps` 每步 / `keySteps` 仅关键步） | 对局模式 |
| **分析（已有）** | 导入 FEN/PGN | 自由模拟双方 | 手动/变更后 | 否 | 手动触发 | —（现有能力） |
| **打谱（复盘）** | 导入 PGN | 逐步回放 | 每步标注 | 否 | 分支讲解 | 分析/复盘 |
| **练习（战术/开局）** | 题库局面 | 求解 + 校验 | 目标着法校验 | 提示 | 结果点评 | 学习（开局/战术） |

> 备注：chess_tutor 的「学习」≈ 本方案的「练习」；本方案额外增加「打谱（PGN 复盘）」这一模式。

## 3. 差异化能力：可点走法点评（平台级一等公民）

这是本产品区别于 chess_tutor 的关键，重构后**不再是某个页面的私有特性，而是平台契约**：

- **协议**：点评文本内联标记，例如 `[move:e2e4]`（UCI 定位）或 `[branch:...]`（变例）。`comment-model` 解析为 token 流。
- **渲染**：`CommentCard` 把 `moveLink` 渲染成可点链接；点击 → `session.gotoNode(对应 FEN)` 并 `BoardView.focus` 高亮该格/该步。
- **价值**：让 AI 点评能「指」棋盘（满足 Tutor 交互硬约束），且同一套能力被对弈/分析/打谱/练习全复用，不重复造。

## 5. MVP 与落地顺序

每个阶段独立可上线、可验证，遵循现有回归测试门禁（`.workbuddy/tests/`）。

- **MVP（P1）：平台化现有 analyze 页**
  - 抽 `L0 session`（线性→树，先支持单主变 + 手动分支）与 `comment-model`；
  - 抽 `L1 BoardView / EnginePanel / CommentCard / MoveTree`；
  - 先用「分析」模式跑通，不新增其它模式。**验证「平台抽象」是否成立**——这是本次重构的最大不确定性，先用已有能力试水，风险最低。
- **P2：SPA 壳 + 对弈模式**
  - Landing 卡片 + Workspace 视图切换；接入 `sparrer` 出着（引擎执黑/白），每步自动分析 + 点评。
- **P3：打谱模式**
  - PGN 导入 → 走法树回放 → 每步引擎标注 + 分支讲解（复用 comment-model）。
- **P4：练习模式（后期）**
  - 战术/开局题库；目标着法校验 + 提示 + 结果点评（依赖 `tactic`/`opening` 数据，需外部题库）。

## 6. 与现有 `agent-plan` 的关系（不废弃）

- 现有 `docs/agent-plan.md`（Tutor/Sparrer 阶段一~三）**不废弃**：Tutor/Sparrer 从「某个功能的阶段」上升为**横切 AI 教练能力（coach-service）**，被所有模式消费。
- 阶段三「Persistent Tutoring Memory」仍是**跨模式**的用户画像 / 错题记忆（对弈记录、分析错题、练习薄弱点统一沉淀）。
- 命名与标识符约定（tutor/sparrer、FEN+UCI、事实/意见分层）全部延续。

## 7. 风险与待确认

1. **主包体积 / 分包**：采用「Landing 主包 + 模式分包」后，共享基础库（session/engine/analysis/coach + 组件）必须放在主包或分包公共依赖里，构建去重，避免每个分包重复打包；别把 4 个模式的薄逻辑 + 共享库全塞进主包（主包上限 2MB）。
2. **走子树 vs 现有线性 `game.js`**：现有 `game.js` 是线性状态机，升级为树是 L0 的最大工作量；遵循「内部 FEN+UCI、PGN 仅边界」约定，避免阶段三错题去重失效。
3. **回归守护**：拆组件时 `analyze-page.test.js` 的 WXML 静态守卫（循环变量/`wx:key`/不用 `<block>`）必须继续满足。
4. **引擎端点**：`engine: remote` 真机可用依赖自有已备案域名（现有 `chess.imex.de5.net` 为香港机，需确认备案/合法域名状态），详见现有 working memory 待办。
5. **待你拍板**：Landing 是否要「继续上次 / 最近棋谱」（依赖 `cloud on` 的跨设备存档，属阶段三连续性能力）；练习模式的题库数据来源（Lichess 公开数据 / 自建）。

## 11. 第二轮澄清与追加决策（2026-10-21）

针对首版方案的用户追问，逐条拍板如下：

### 11.1 服务职责划分（见 §2.1b）
3 线 MultiPV = `engine-service`（算原始 N 线）+ `analysis-service`（读成 3 线 + 评分，节点级缓存）；AI 点评 = `coach-service`（吃 3 线 + 局面 → LLM）。依赖链 engine→analysis→coach 已清晰，重构即把 analysis/coach 从 `ai-client.js` 物理拆离。

### 11.2 导航架构：Landing(主包) + 模式分包页（见 §1）
澄清：小程序无 HTML 页面；多 page ≠ 主包增大（靠分包）；重建可控（全局 store + 引擎无状态/纯函数）。默认推荐分包多页，SPA 单页双视图为可选。

### 11.3 来源标注 `degraded` 的语义
`source` 只有 `'remote'` / `'local'` 两种真值。**`degraded` 不是第三种来源**，而是落在 `source:'local'` 结果上的标记（`degradedFrom` + `degradedReason`），含义是「本想用 remote，远端不可用，被动回落 local，棋力偏弱」。它与「用户主动选 local 模式」（无 `degradedFrom`、无 notice）必须区分：前者是系统兜底且强度低于预期，后者是用户知情选择。`describeEngineSource` 已据此返回 `degraded: !!notice`。

### 11.4 自动触发 AI 点评 → 用户可自行设置
新增设置项 `autoCoach`，三档含义（AI 点评消耗 token，故交由用户决策）：
- **`off`**：**从不自动**，只有用户手动点「生成点评」才出（最省 token，推荐给在意额度的人）。
- **`on`**：**总是自动**——无论端上（`local` 弱引擎）还是云端（`remote` 强引擎）模式，分析完成后都自动出点评。
- **`remoteOnly`**：**仅云端强引擎模式下自动**；本地弱引擎模式不自动。

`remoteOnly` 的考虑：AI 点评的质量建立在「引擎 3 线分析」的可靠度之上。云端 Stockfish 分析强、点评有依据；本地弱引擎分析偏差大，此时自动点评既产出低价值内容、又在烧 token（双输）。所以把"自动"限制在强引擎场景，弱引擎场景留给用户手动按需触发。**保留三档**（用户已拍板），设置页用一行小字向用户解释这一动机。

> **设置页文案（写入 UI，解释 `remoteOnly` 动机）**：
> 「自动点评会消耗 AI 额度。
> · 关闭：完全手动，最省额度。
> · 总是：每一步都自动点评（含本地弱引擎）。
> · **仅云端**：只在连接云端强引擎时自动点评——本地弱引擎的分析不够可靠，自动点评既不准又费额度，建议留给手动触发。」

#### 对弈模式子策略：仅关键步自动点评
对弈模式每步都触发引擎分析，若 `autoCoach` 为 `on`/`remoteOnly` 仍每步都自动出点评，**token 消耗与界面打扰都很重**。因此增加**对弈专属子开关** `playCoachScope`（在「设置 / 对弈」内，仅对弈模式生效）：
- **`allSteps`（每步）**：每步分析完都自动点评（默认，最完整）。
- **`keySteps`（仅关键步）**：**只在「关键步」自动点评**，其余走子只做引擎分析、不自动出点评，用户想看某步点评可手动点。
  - **「关键步」判定**（纯引擎、确定性、不依赖 LLM）：本步相对上一步的**评估波动 |Δcp| ≥ 阈值（默认 80cp，约一兵）**，或本步为**吃子 / 将军 / 送将**等使评估显著变化的着法。阈值在设置页可调（保守/标准/宽松三档）。
  - 这样把 token 花在「局势真正变化的时刻」（失误、战术、转折），安静的过渡着法不烧额度也不刷屏。
模式配置层（§2.3）的「点评触发」列改为读取 `autoCoach` +（对弈时）`playCoachScope`，而非写死。

### 11.5 第三方 LLM 可配置 + 与公众平台切换
新增 **`llm-provider` 抽象层**，支持两种提供方：
- `platform`：现状公众平台云 SDK（`cloud-config.publicConfig` 的 endpoint + publishableKey），不暴露 key 给用户。
- `openai-compatible`：用户在设置页填 **BASE_URL + API_KEY + model**，直连 OpenAI 兼容接口（DeepSeek / GLM / OpenRouter 等）。
设置页可切换「当前激活的提供方」。**安全提醒（必须写进设置页）**：把 API_KEY 放前端会随包被提取，个人自用可接受；发布分发建议走自有代理（扩展 `chess.imex.de5.net` 加 `/llm` 代理，key 留服务端）；直连第三方还需在小程序后台把第三方域名加进 request 合法域名。

> **为什么"前端存 key 会被提取"**：微信小程序的代码包（`.wxapkg`）本质是**明文打包**——JS 逻辑代码仅压缩、未强加密/混淆。任何人拿到包（从微信本地缓存目录、或已安装包反编译）都能解出里面硬编码的 key；即使用 `wx.setStorageSync` 存进本地存储，同设备下也能被读出。客户端里出现的任何"密钥"都不会真正保密（网页 F12、App 逆向同理）。因此：用户**自己**填的第三方 key 属个人自用、风险自担（被提取顶多是别人用他的 key）；但**开发者想内置/代理给所有用户用的 key** 绝不可进前端，必须服务端持有（自有代理转发并注入 key）。
>
> **关于"本地加密存储是否更安全"的结论**：**不会本质更安全**。若 key 在前端被使用（直连第三方 LLM），客户端迟早要**解密**它，而解密密钥/逻辑也一同打包在 `.wxapkg` 里——攻击者拿到包后先解出解密逻辑、再解出密文，与明文存储只差一步逆向。加密只是**提高一点点门槛（混淆，obfuscation），不是保密（confidentiality）**。真正保护密钥只有一条路：**不让密钥进客户端**（走自有代理，服务端持有 key）。故本方案对第三方 key 仍维持"个人自用可接受、开发者内置不可取"的口径，不把加密存储当成安全手段。

### 11.6 剪贴板自动读取 FEN/PGN（含图片限制）
- **文本（可行，纳入 MVP）**：Landing（及各模式 page）`onShow` 调 `wx.getClipboardData()`（**仅文本**），若匹配合法 FEN/PGN 正则，弹 `wx.showModal`：「是否导入剪贴板中的棋局？」确认即解析载入。
- **图片（技术限制，改后续阶段）**：微信小程序**无法读取剪贴板里的图片**（`wx.getClipboardData` 只回文本）。故「自动检测剪贴板图片」做不到。改为后续阶段：用户主动 `wx.chooseMedia` 从相册选图 → 后端识别（扩展 server 加 `/recognize`）→ 载入。与用户「图片导入作为后续阶段」一致，但入口是「主动选图」而非「剪贴板自动检测」。

### 11.7 内容过多易迷失 → 交互研究待办（不现在定稿）
多线引擎结果 + 富文本点评 + 可点局面，初学者确实易迷失。列为**交互研究 backlog（P1 之后）**，候选方向：
- 渐进展示：默认只给「主线 1 条点评 + 关键分支」，展开才看更多；
- 局面导航「面包屑 / 一键回溯栈」：点分支链接后能从讲解路径一键退回主点评；
- 「聚焦讲解模式」：把一条点评变成引导式走子序列，每步棋盘自动走到对应局面并解说，而非一次性铺开所有分支；
- 分支树（MoveTree）局部展开而非全展开；
- 每个可点局面点击后强化 `BoardView.focus` 高亮讲解涉及的棋子/格子。
