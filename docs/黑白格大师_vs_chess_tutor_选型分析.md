# 选型分析：继续做「黑白格大师」，还是把 chess_tutor 改成小程序？

> 分析日期：2026-10-10
> 对象：chess_tutor（E:\projects\chess_tutor，Next.js Web 应用）
> 已知前提：「黑白格大师」= 原生微信小程序 + 云开发，核心已跑通、缺深度功能，未上线、无用户、无必须保留资产，目标是商业变现。

---

## 0. 结论先行

**推荐：继续「黑白格大师」，把 chess_tutor 当成「参考实现 / 产品蓝图」，而不是「代码基座」。**

三条决定性理由：

1. **授权是硬伤。** chess_tutor 整体是 GPL-3.0，且项目的 `LICENSING.md` 白纸黑字写明：第三方 fork「不可以做专有移动端」「任何你基于该代码构建的移动应用必须以 GPL-3.0 分发」。你的目标是商业变现 + 闭源，这与 GPL 直接冲突。
2. **能直接用的代码只占约 7%。** 全项目约 2.5 万行里，真正零 DOM 依赖、可搬进小程序的纯逻辑只有约 1900 行；占大头的 UI 层（React 19 + react-chessboard + 两个上千行的巨型组件）在小程序里 100% 用不上。
3. **你已经跑通的部分，恰恰是 chess_tutor 里最难搬的部分的反面。** 棋盘、走子、对战在小程序端你已经有了；而 chess_tutor 的棋盘 UI 你反而完全用不了。换基座等于把已经做完的部分扔掉，去重写一套你本来就会的东西。

**唯一应该考虑「以 chess_tutor 为基座」的情况**：你接受把自己的小程序也整体 GPL 开源（那付费墙基本不成立），或者你去向原作者（stefan-kp / KaProblem）拿到商业授权。

## 1. chess_tutor 功能全景

### 1.1 产品定位

一个**「会说话的 AI 国际象棋教练」**：你跟 Stockfish 下棋，同时 LLM 在旁边实时点评、讲解、回答提问。它不是棋类对战平台，而是**教学产品**——核心价值在「每一步都有解释」。

### 1.2 三大模式

| 模式 | 做什么 | 关键设计 |
|---|---|---|
| **对局模式** | 与 Stockfish 下整盘棋，AI 实时讲解 | 每一步后自动分析：走子质量、胜率变化、漏掉的战术、开局理论、局面要点；可随时向教练提问；认输也有「人设化」回应 |
| **开局训练** | 选一个开局，按谱走 | 12,379 条 ECO 开局库；走偏时弹窗让你选「悔棋回谱 / 转完整对局 / 继续探索」；配维基百科背景讲解；会话可断点续练 |
| **战术训练** | 按主题刷战术题 | 8 个主题（牵制、击双、串击、闪击、双重攻击、超载、底线弱点、困子）；连对数与正确率统计 |

### 1.3 技术底座

- **框架**：Next.js 16（本机实际装 16.4.0）+ React 19 + Tailwind 4 + TypeScript
- **棋规**：chess.js 1.4.0（纯 JS，可移植）
- **棋盘**：react-chessboard 5.8（DOM 渲染，小程序不可用）
- **引擎**：stockfish.js 10 —— **浏览器内跑 WASM**（`stockfish.js` 1.58MB + `stockfish.wasm` 559KB + `stockfish.wasm.js` 96KB ≈ 2.2MB）
- **LLM**：已改造为 OpenAI 兼容协议，支持自定义 Base URL / Key / Model（见记忆：2026-10-09 的重构），**由浏览器直连 provider，用户自带 Key**
- **国际化**：自研类型安全方案，7 种语言（en/de/fr/it/pl/zh-CN/zh-TW），`translations.ts` 1907 行
- **测试**：23 个测试文件、233 个 jest 用例全绿，另有 7 个 Playwright e2e spec

### 1.4 真正值钱的三个东西

按「稀缺程度 / 自己造的成本」排序：

1. **战术识别引擎**（`tacticDetection.ts` 383 行 + `tacticalLibrary.ts` 824 行）
   每步棋后自动识别你「漏掉了什么」：安全吃子（带反吃判断）、牵制、击双、串击、将军、悬子。有多层过滤器压误报。这是整个项目最具差异化的部分，也是唯一需要一定棋类算法功底才能写好的模块。
2. **提示词工程**（`tutorPrompt.ts` / `analysisPrompts.ts` / `personalities.ts`）
   9 种教练人格（开局教授、职业教练、醉酒俄派 GM、炸裂主播、甘道夫、纯 Stockfish、嘴臭玩家、莎士比亚、禅师），每种人格的系统提示词 + 语言控制 + 上下文注入（FEN、评估、开局、战术）的组合方式是调过的。
3. **数据资产**：ECO 开局库 12,379 条（8.6MB，含 4.6MB 的 moveIndex）+ Lichess 战术题库管道。

### 1.5 实测发现：有几处「宣传 > 实际」

这些是读代码发现、README 里看不出来的，直接影响你对它价值的判断：

| 宣传 | 实际情况 |
|---|---|
| 「每类战术 20+ 题，来自 Lichess 数据库」 | **默认只有 31 题**（8 个主题各 3–4 条，overloading 仅 3 条）。代码 `tacticalLibrary.ts` 是直接 `import` `fixtures/tactics/*.json` 的，这些 JSON 就是测试 fixture。要拿到 Lichess 的 560 万题库，必须先跑 `python3 scripts/setup_tactical_puzzles.py` 或 Docker 启动脚本去下载并**覆盖写回** fixture 文件。不跑就是 31 题。 |
| 「Wikipedia 开局背景」 | `public/wikipedia/` 是空的（只有 `.gitkeep`），缓存要靠 `npm run cache:wikipedia` 生成；服务端 `GEMINI_API_KEY` 没配时，`/api/v1/llm/opening-explanation` 永远走兜底文案。 |
| 「Mobile Apps（iOS/Android）」 | Capacitor 依赖在，但移动构建会**剥离 Stockfish.js** 并强制走 `RemoteEngine`，等于移动版是另一套架构，且只有版权持有者能专有分发。 |
| 代码质量 | 存在 `ChessGame.tsx`（1031 行）、`Tutor.tsx`（1112 行）这类巨型组件，还有 `OpeningTrainingContext.old.tsx` 这种没清理的旧文件。属于「个人项目 + AI 辅助生成」的典型形态，不是可以长期二开的工程化底子。 |

## 4. 「把 chess_tutor 改成小程序」要付出的代价

### 4.1 授权（最关键，先于一切技术讨论）

- 项目是 **GPL-3.0**（`LICENSE`），且因为内置 Stockfish.js（同样 GPL-3.0）而无法规避。
- `LICENSING.md` 明确：**第三方 fork 者「不可分发专有移动应用」「不可移除 GPL 要求」「不可主张版权持有者权利」**；「任何你构建的应用必须以 GPL-3.0 分发」。
- 微信小程序属于「分发到用户设备」，会触发 GPL 义务。而 GPL 要求向所有接收者开放源码、且不得限制再分发——**这与付费墙/会员制商业模式本质冲突**。
- 有人会说「我不复制代码，只抄思路」——注意：读源码后照着写，在法律上仍可能被认定为衍生作品。若走这条路，**建议由未接触过该项目源码的人实现，或只参考公开的棋类算法通识**（战术识别本质是通用算法，任何棋类教科书都有）。
- 若你确实想要这套代码，正道是联系原作者买商业授权（dual licensing 是版权持有者的权利）。

### 4.2 技术栈：等于重写

- Next.js 路由、React 组件、Tailwind 全部作废。要么改用 Taro / uni-app 重写 UI，要么用 web-view 套壳。
- web-view 套壳有额外问题：**个人主体小程序不支持 web-view 组件**；且微信对「纯网页打包」的小程序审核趋严，有被拒风险。
- react-chessboard 是 DOM 棋盘，小程序要用 canvas 或 view 重写棋盘组件（你已经有现成的了）。

### 4.3 包体积

- 微信小程序主包 ≤ 2MB，总包上限 20MB（以官方最新文档为准）。
- 单是 Stockfish WASM 就 2.2MB，开局库 8.6MB —— **都不可能进包**，必须放服务端按需返回。
- 而且小程序 WebAssembly 支持有限（无 SIMD、无多线程、内存受限），Stockfish 的 NNUE 版本在小程序里基本跑不动。**结论：引擎必须服务端化。**

### 4.4 服务端是绕不开的

想保住 chess_tutor 的核心体验，后端至少要提供三样东西：

1. **Stockfish 分析服务**（CPU 密集、需常驻进程）
2. **开局库查询服务**（8.6MB 数据 + moveIndex）
3. **LLM 中转服务**（小程序不能直连 openai.com 这类未备案域名）

这与你现在的**云开发**架构有冲突：云函数不适合跑 Stockfish（无常驻进程、CPU 和超时都受限）。可行解是 **微信云托管**（可跑常驻 Docker 容器，且默认域名可直接配置为小程序 request 合法域名，省掉自己 ICP 备案的麻烦）。

### 4.5 合规（商业变现必须提前想）

- AI 生成内容在微信小程序内属于敏感类目：需要关注生成式 AI 相关标识与内容审核要求，个人主体基本做不了 AI 问答类。
- 教学/培训类目可能涉及资质要求。
- 这些不是技术选型问题，但会决定你能不能上线、能不能收款。

### 4.6 工作量粗估

| 路线 | 主要内容 | 粗估周期 |
|---|---|---|
| **A. 继续黑白格大师，自建深度功能** | 战术识别（重写 300–500 行）、AI 讲解（提示词 + 中转）、开局库服务、Stockfish 服务 | 4–8 周出 MVP |
| **B. chess_tutor 改小程序** | UI 全重写（Taro/uni-app，20+ 组件、2.5 万行里的绝大部分）、后端三件套、存储改造、合规 + 授权 | 8–16 周，且授权问题无法用时间解决 |

## 5. 推荐方案：以黑白格大师为主干，定向吸收 chess_tutor 的「能力设计」

分四步，每一步都能独立上线、独立验证：

**第一步：补 AI 讲解（价值最高、成本最低）**
- 参考 chess_tutor 的上下文注入方式：把 FEN、走子、评估值、识别到的战术一起塞进提示词。
- 后端用云托管起一个极简 Node 服务做 LLM 中转（顺带解决域名白名单问题）。
- 人格先做 2–3 个，不要一上来做 9 个。

**第二步：加引擎分析**
- 云托管容器里跑 Stockfish，提供 `/evaluate`（FEN → 最佳着法 + 评分）。
- 先只做「每步评分 + 最佳着法」，这是评估条和复盘的基础。

**第三步：战术识别（自己写，不要抄代码）**
- 用 chess.js 生成合法着法，按通用定义判定牵制/击双/串击/将军/悬子/安全吃子，约 300–500 行可实现。
- 关键是对照 chess_tutor 的**产品行为**（什么时候提示、怎么避免误报、怎么把结果喂给 LLM），而不是复制它的代码。

**第四步：开局库**
- ECO 开局数据是公开数据集，Lichess 题库也是公开数据，直接用公开来源自建即可，无需碰 chess_tutor 的文件。
- 放云数据库或对象存储，按需查询，别进包。

**商业化提醒（比技术选型更重要）**：国内国际象棋受众远小于围棋/中国象棋，C 端付费天花板有限。如果想变现，认真考虑面向**少儿国际象棋培训**——家长付费意愿明确，机构有采购预算，B 端（教练端 / 机构版）可能比 C 端更容易收到钱。建议先用最小 MVP 验证有没有人愿意付钱，再决定投入深度。

## 6. 需要你核实的事项

1. **是否愿意 GPL 开源你的小程序全部代码**？如果愿意，chess_tutor 可以直接当基座；不愿意，就只能参考设计。
2. **你的小程序主体是企业还是个人**？决定是否能用 web-view、能否做 AI 类目、能否收款。
3. **cloudbase 云托管是否在你的预算内**？Stockfish 常驻容器是按量计费的，商业变现下要算清单次分析成本。
4. **Lichess 题库与 ECO 数据的许可**：建议直接采用公开数据源（Lichess 数据库为公开数据，具体条款以官方为准；ECO 集合源自 ragizaki/ChessOpeningsRecommender，许可需核实后再商用）。
