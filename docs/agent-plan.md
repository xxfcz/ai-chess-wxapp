# 深思·教练 / 陪练：AI Agent 化产品与技术规划

> 本文档是把现有「国际象棋 AI 分析」小程序升级为**真正 Agent** 的总纲。  
> 阶段细节见配套的三份文档：  
> `docs/agent-phase1-tutor.md`（阶段一）· `docs/agent-phase2-react.md`（阶段二）· `docs/agent-phase3-memory.md`（阶段三）
>
> 配套代码：`utils/ai-client.js`、`utils/coach-demo.js`、`utils/engine.js`、`utils/game.js`、`pages/analyze/*`  
> 测试门禁：`.workbuddy/tests/{engine-and-game,analyze-page,cloud-adapter}.test.js`（现 401 项断言全绿）  
> 更新日期：2026-10-07

## 0. 一句话定位

现有实现已经是「Agent 的胚胎」——有感知（FEN + 棋盘交互）、有确定性推理（端上引擎）、有行动（给建议、演示线）、有反馈（用户走子回到新局面）。  
缺的是三样东西：**工具协议、自主循环、记忆**。补上这三样，它才是 Agent。

一句话概括本轮改造的核心原则：

> **别把 LLM 当文案生成器用，把它当规划器用；所有确定性计算全部下沉成端上工具。**

## 1. 两个角色与术语表

产品形态定为两个角色。**本轮聚焦教练，陪练仅作占位描述。**

### 1.1 为什么「陪练」用 Sparrer 而不是 Opponent

四个候选词的语义差别比看起来大：

| 词                  | 语义            | 隐含的用户关系    | 评价                                           |
| ------------------ | ------------- | ---------- | -------------------------------------------- |
| `opponent`         | 棋局中的对方        | 中立、无感情色彩   | 准确但冰冷，暗示「与你对立的人」                             |
| `rival`            | 竞争者、劲敌        | 争夺同一目标的对手  | 宿敌叙事，语气过重，偏离练习场景                             |
| `sparring partner` | 拳击/武术中的**陪练** | **帮你变强的人** | 语义最准确，但**两个词带空格**，进函数名/字段名/存储键时笨重且大小写不统一     |
| **`sparrer`**      | 同上，单词形式（陪练者）  | **帮你变强的人** | ✅ 语义与 `sparring partner` 一致，且是单个小写词，可直接用作标识符 |

选词上多说一句：`sparer` 才是词典里更常见的拼写，本项目**统一写作双写 r 的 `sparrer`**，把它当成项目术语固定下来，不再纠结拼写。

关键差别在于**目的**：

- 一个 `opponent` 的目的是**赢你**。用它命名，产品会不自觉往「提高胜率」优化——于是最高水平的引擎成了最优解，结果是用户每局被虐，体验很差。
- 一个 `sparrer` 的目的是**让你练到东西**。它的最优解是「刚好比你强一点、且恰好在你薄弱的地方施压」，胜负反而不是目标。

这个命名不是文字游戏，它会在后续每一个 design trade-off 里起作用（尤其是阶段三的记忆层：记住用户的弱项，是为了针对性喂招，而不是为了赢）。

### 1.2 术语表

为免文档与代码中英混用造成歧义，全项目统一按下表用词。**新增代码一律按「代码标识符」列命名**；既有标识符的处理见 §1.4。

| 中文  | 英文（文档用词）   | 代码标识符       | 说明                           |
| --- | ---------- | ----------- | ---------------------------- |
| 教练  | Tutor      | `tutor`     | 本轮聚焦。讲解局面、回答「为什么」            |
| 陪练  | Sparrer    | `sparrer`   | 占位。会下棋、带风格的对手                |
| 工具层 | Tool Layer | `tools.js`  | 端上确定性能力的集合，供模型调用             |
| 候选  | Candidate  | `candidate` | 端上预生成的合法走法，带编号               |
| 演示线 | Demo Line  | `demoLine`  | `===DEMO===` 里的可视化分支（沿用现有协议） |
| 轮次  | Turn       | `turn`      | 一次用户提问到模型最终答复的完整往返           |
| 预算  | Budget     | `budget`    | 一轮对话允许消耗的工具调用/时间/节点上限        |

> 注一：`opponent` 仍可在棋理相关语境里作为普通名词使用（如「对手的王不安全」），  
> 但**不指代本产品的角色**。角色一律叫 `sparrer`。
>
> 注二：`coach` 是**既有代码标识符**（`COACH_SYSTEM_PROMPT`、`utils/coach-demo.js`、`onCoach`、`coachText`）。  
> 角色名统一为 `tutor`，但**历史代码标识符不在本轮重命名范围内**——改名收益低、回归风险高，  
> 新旧对照见 §1.4。

### 1.3 陪练（Sparrer）· 简要占位

> 本轮只做占位，**不进入阶段一到三的开发范围**。以下为方向性描述，细节留待后续展开。

**产品形态**：用户选定棋力档位与风格后，直接与之对弈；对局中可随时暂停，切换到 Tutor 视角讲解刚才那步。

两条已知的关键结论，先记下来以免将来踩坑（**它们都意味着陪练本质上是独立的调参项目，不该和教练混在一起做**）：

1. **「棋风」是评估函数权重，不是 system prompt。**  
   「喜欢乱战的对手」= `{ material: 0.8, aggression: 1.6, kingSafety: 0.6 }`，应该做成 `engine.analyze` 的 `weights` 参数。  
   用它写 prompt 只会得到一个嘴上说激进、实际走法依旧平庸的对手——因为最终决定出手的是搜索器，不是语言模型。
2. **棋力分级 ≠ 降低搜索深度。**  
   降深度只会产出「又弱又不像人」的对手：弱是因为看得浅，不像人是因为它依然不会犯只有人会犯的错。  
   正确做法是**固定在中等深度，按 softmax 在 top-k 候选里按温度采样**——弱的 AI 偶尔选次优，但不会随机送子。

陪练与教练**共用 `utils/tools.js` 工具层**，这也是建议等教练跑到阶段二稳定后再开陪练的主要原因。

### 1.4 角色名与既有代码标识符的对照

角色名改为 `tutor` 后，代码里仍会大量看到 `coach`。**这是有意为之，不是漏改**：

| 既有标识符                      | 角色归属            | 是否重命名                                     |
| -------------------------- | --------------- | ----------------------------------------- |
| `COACH_SYSTEM_PROMPT`      | Tutor 的系统提示词    | ❌ 保留。改名要同步动测试与常量引用，收益低于风险                 |
| `utils/coach-demo.js`      | Tutor 的演示线解析/回放 | ❌ 保留。文件名变更会牵动所有 `require` 路径              |
| `onCoach` / `coachText`    | 页面上的点评入口与文案字段   | ❌ 保留。`coachText` 还是 `setData` 的键名，牵动 WXML |
| `ai.requestCoachComment()` | Tutor 的云端点评请求   | ❌ 保留                                      |
| **新增**的一切                  | ——              | ✅ **一律用 `tutor` / `sparrer`**             |

判断原则很简单：**新写的用新名，既有的不动**。等哪天因为别的原因整体重写 `ai-client.js` 时，顺手统一即可，不必现在付这个代价。

> 反过来的坑更要避开：不要出现「同一个概念一半叫 `coach`、一半叫 `tutor`」的**新代码**。  
> 新增文件（如 `utils/tools.js`）与新增字段（如 prompt 里的候选段）必须清一色 `tutor`。

## 2. 现状诊断：为什么它「还不是」Agent

### 2.1 最大的技术债：让模型写 SAN

`utils/ai-client.js` 的 `COACH_SYSTEM_PROMPT` 里有这么一段：

> 每个子都要真的能走到那个格子（注意不要被自己或对方的棋子挡住、不要吃不存在的子、将军时才加 +）；  
> 不确定能走到的着法宁可不写，也不要猜测；

**这是在用提示词对抗幻觉。** 它是当前实现最脆弱的地方：空间推理本就是语言模型的弱项，靠文字约束换来的只是「大部分时候对」。

好消息是 `utils/coach-demo.js#resolveMoves` 已经在做事后校验——逐手 `Game.applySan` 校验，非法就 `console.warn` + 截断保留合法前缀，全废才丢整条。所以现状**不是「幻觉走法上了棋盘」**，而是：

> 模型一猜错，推荐演示线就被截断甚至整体消失，正文里的走法链接跟着失效。

用户感知到的症状是「点评里提到一个很有意思的后续，但点不了」——**最精彩的那一半经常恰好是被丢掉的那一半**。

### 2.2 Agent 化的收益不在「更聪明」，而在「更可靠」

把走法生成从模型手里拿走，收益有三层，且一层比一层大：

1. **幻觉归零**（阶段一）：走法序列 100% 由 chess.js 生成。`COACH_SYSTEM_PROMPT` 那段可以直接删掉一半。
2. **模型开始能做真正的推理**（阶段二）：有了 `expandLine`，它才可能回答「为什么 Ke2 不好」——自己去看 Ke2 之后会发生什么，而不是对着 prompt 里三条现成结论复述。这才是讲解，不是转述。
3. **长期个性化**（阶段三）：从「每次都是陌生人」变成「记得你上次栽在哪」。

## 3. 三阶段总览

|        | 阶段一 · 落地基座            | 阶段二 · 多轮 ReAct     | 阶段三 · 记忆                   |
| ------ | --------------------- | ------------------ | -------------------------- |
| 代号     | Candidate Grounding   | Reason-Act Loop    | Persistent Tutoring Memory |
| 一句话    | 模型提意图，端上生成合法序列        | Agent 自己决定要查什么、查几次 | 记住你是谁、栽在哪                  |
| LLM 往返 | 仍为 **1 次**            | **1~N 次**（受预算约束）   | 同阶段二，附加历史上下文               |
| 用户可感知  | 演示线不再消失、能点            | 可以追问「为什么不能 Nc3」    | 点评开始提到「你上次也是…」             |
| 新增依赖   | **无**                 | 无                  | 云 DB（按 openid）             |
| 主要风险   | prompt 变长致 token/延迟上升 | 端上搜索被自己拖死          | 隐私、存储成本、画像漂移               |
| 依赖     | 无                     | 阶段一的工具层            | 阶段二的会话结构                   |

**投入产出比最高的是阶段一**：不新增依赖、不动 `engine.js` 契约、不改 `app.json`，复杂度增加约 20%，拿到约 80% 的收益，延迟几乎不变。**建议先做它。**

## 4. 跨阶段共享契约（冻结层）

> 这一节是本文档**唯一不该随实现随意变动**的部分。  
> 理由：正因为代码会变，协议才更需要提前定死——否则阶段二写工具的人按一种形状、阶段三写记忆的人按另一种，最后两边打架。

### 4.1 分层职责

```
┌──────────────────────────────────────────────────────┐
│ LLM（规划与表达）                                      │
│   决定看什么、怎么组织语言、给什么建议                    │
└────────────────────┬─────────────────────────────────┘
                     │  结构化意图（不是走法）
┌────────────────────▼─────────────────────────────────┐
│ Tool Layer（utils/tools.js —— 端上、确定性）            │
│   零延迟 · 零成本 · 离线可用 · 可高频调用                │
│   ├── legalMoves(fen, opts)                          │
│   ├── expandLine(fen, moves, depth)                  │
│   ├── describePosition(fen)                          │
│   └── analyze(fen, depth, multiPV)  ← 复用现有契约      │
└────────────────────┬─────────────────────────────────┘
                     │
┌────────────────────▼─────────────────────────────────┐
│ 事实层：chess.js + engine.js（不许绕过）                │
└──────────────────────────────────────────────────────┘
```

**铁律：走法只能由 chest.js 产生。** 任何环节都不接受由字符串拼接/模型生成/猜测得来的走法——除非先过合法性校验。

### 4.2 工具层接口签名

```js
// utils/tools.js —— 纯逻辑，无 wx 依赖，可单测

/**
 * 合法走法候选池。
 * @returns {Array<{uci:string, san:string, from:string, to:string,
 *                  piece:string, capture:boolean, check:boolean, mate:boolean}>}
 */
legalMoves(fen, { only, limit })

/**
 * 从任意局面出发，逐手施加给定走法并返回每一步之后局面的评估。
 * moves 可以是 SAN 数组或 UCI 数组；任一步非法即返回已成功的部分。
 * @returns {{ path: Array<{ply:number, san:string, uci:string, fenAfter:string,
 *                          whiteCp:number|null, best:string|null}>,
 *             complete: boolean, failedAt: number|null }}
 */
expandLine(fen, moves, { depth })

/**
 * 局面的结构化特征，用于降低模型「读 FEN」的负担。
 * @returns {{ material:{w:number,b:number}, mobility:{w:number,b:number},
 *             kingSafety:{w:string,b:string}, pawn:{doubled:number, isolated:number},
 *             openFiles:string[], phase:string }}
 */
describePosition(fen)
```

**实现约束（继承自 AGENTS.md §5，勿违反）**：

- 搜索树内部**必须**用 `raw_moves()/raw_move()/raw_undo()`，`chess.moves({verbose:true})` 的 SAN 生成是 O(n²)、实测慢约 13 倍；
- SAN 只在**返回值处生成一次**；
- 不 import 页面、不碰 `wx`、不读 DOM。

### 4.3 工具产物的压缩原则

**永远不要把整棵 PV 树塞回对话。** 工具结果回传前必须压缩：

| 回传内容                | 不要回传          |
| ------------------- | ------------- |
| 分数**差**（「比最佳差 1.2」） | 原始 cp 数组      |
| 关键 2~3 手            | 完整 PV（可能十手以上） |
| 结构化短标签（「丢子」「王暴露」）   | 完整 FEN 串的堆砌   |

理由：每多一个 token 都是真金白银的延迟（该模型 ~3s 完成一次点评），而 PV 后段对「这一手好不好」的判断边际收益极低。

## 5. 继承的硬约束（改代码前必读）

这些是本项目已经踩过的坑，Agent 化过程中**每一条都会被再次遇到**：

| # | 约束                                  | 出处                      | 阶段影响                   |
| - | ----------------------------------- | ----------------------- | ---------------------- |
| 1 | 棋盘不用 Canvas，用 view 网格 + 字形          | AGENTS.md §6.1          | 阶段二的中间态也要能渲染           |
| 2 | 按格取子必须 `board[7 - rank]`            | AGENTS.md §6.2          | 工具层若渲染出错从这里查           |
| 3 | `wx:for` 元素**自身属性**不得引用循环变量 `index` | AGENTS.md §6.4          | 多轮对话气泡列表必踩             |
| 4 | `wx:key` 用字符串字段，不用 `<block>`        | AGENTS.md §6.4          | 同上                     |
| 5 | 搜索树内勿用 `moves({verbose:true})`      | AGENTS.md §5            | 工具层的核心性能约束             |
| 6 | 端上分析必须与云端能力**解耦**                   | AGENTS.md §8            | **工具层不依赖网络，任何环境都必须可用** |
| 7 | 单次会话**锁定同一个模型**                     | 现有 `cachedModelId`      | 多轮下每轮重探模型既慢又贵          |
| 8 | 重试粒度需从「单次请求」上提到「会话层」                | 现有 `shouldTryNextModel` | 一轮失败 ≠ 整轮对话失败          |
| 9 | `TextDecoder` 缺失（真机）、流式适配、超时看门狗     | AGENTS.md §7            | 多轮下**每轮都会遇到**          |

### 5.1 唯一的真瓶颈：网络往返，不是算力

因为工具跑在端上、执行几乎零耗时，多轮 ReAct 的成本集中在**每次 LLM 往返的延迟**（实测 fast 模型 3~10s/次）。

推论：**超时预算应按「整轮会话」分配，而不是按「单次请求」叠乘。**  
否则三轮下来累计等待会突破用户忍耐阈值。具体的预算模型见阶段二文档 §4.3。

## 6. 决策记录

> 记「为什么这么定」，不记「改哪一行」。半年后想推翻某个接口时，需要的是当初的理由。

| #  | 决策                          | 理由                                     | 若推翻需重做                 |
| -- | --------------------------- | -------------------------------------- | ---------------------- |
| D1 | 先做阶段一，且**不引入任何新依赖**         | 20% 复杂度换 80% 收益；不触碰已稳定的 `engine.js` 契约 | 整个工具层                  |
| D2 | 走法**永不由 LLM 生成**，模型只输出意图/编号 | 这是对幻觉的根治，而非缓解；换任何模型都成立                 | 提示词 + `coach-demo` 解析层 |


| D3  | 工具层用**端上 JS**，不上云                          | 零延迟零成本离线可用；本项目最大优势                     | 全部延迟预算与离线可用性             |  
| D4  | 阶段一**复用已有分析结果**，不额外跑搜索                     | 页面 `_lastResult` 已含 3 条线及 PV，成本为零      | 需重新评估性能                  |  
| D5  | `===DEMO===` 协议**向后兼容**，保留 `moves` 字段的兜底路径 | 模型不一定立刻完美遵循新格式，渐进切换                    | `coach-demo` 容错策略        |  
| D6  | 对手角色命名 `sparrer` 而非 `opponent`             | 产品目标是「让你练到东西」而非「赢你」，影响每个 trade-off     | 仅在陪练立项时                  |  
| D7  | 棋力分级用**温度采样**，不用降深度                        | 降深度产出「又弱又不像人」的对手                       | 仅陪练                      |  
| D8  | 重试粒度上提到会话层                                 | 一轮失败不等于整轮失败，否则用户被误判为「服务不可用」            | `shouldTryNextModel` 及周边 |  
| D9  | 记忆按 openid 隔离，且**默认可解释**                   | 隐私敏感；用户应能看到画像并能清除                      | 数据结构与 UI                 |  
| D10 | 阶段二、三**不预先写死函数级改造清单**                      | 代码会变，提前定死将成为维护负担                       | 无（本决策本身就是为了省成本）          |
