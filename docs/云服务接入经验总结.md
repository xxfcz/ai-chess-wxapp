# 云服务接入经验总结（黑白格大师）

> 适用场景：小程序上架 / 重建 / 重新发布之后，需要让「生成点评」（AI 教练）等功能跑通真实云端 LLM。
> 应用：`wbapp_XuxCaYOHVeBjdrJ4UfSMX6`（黑白格大师）
> 处理完成时间：2026-10-08

---

## 0. 一句话结论

「生成点评」依赖真实云端 LLM，**必须**先开通云服务、再把代码里的云凭证对齐到当前应用、补隐私清单、最后用真实调用验证数据面。
只跑单元测试无法证明云可用——这一步是本轮最容易漏、也最隐蔽的坑。

---

## 1. 背景

- 应用「黑白格大师」由「发布为应用」步骤创建（`wbapp_XuxCaYOHVeBjdrJ4UfSMX6`）。
- 该应用的「生成点评」功能（AI 教练）需要真实 LLM 后端：`utils/ai-client.js` 走
  `cloud.llm.models.list()` + `cloud.llm.chat.completions.create({ stream: true })`，
  由 `utils/cloud.js` 通过 `createMiniProgramWorkBuddyCloud({ endpoint, publishableKey, ... })` 接入。
- 接入**代码**本身是现成的，但凭证指向的是**旧应用**，所以真正要做的是「开通 + 改指向」，不是重写逻辑。

---

## 2. 处理过程与每步的必要性

### 2.1 开通云服务（复用指定 applicationId）

- **动作**：用 `reuse` 模式绑定 `wbapp_XuxCaYOHVeBjdrJ4UfSMX6`。
- **结果**：`billingStatus=normal`、`provisionStatus=assigned`、`reusedExisting=true`。
- **必要性**：
  1. 生成点评需要真实云端 LLM，本地 / 模拟环境无法提供，`models.list` 与 `chat.completions` 都会失败。
  2. **必须复用用户指定的 app**，不能顺手新建一个。否则会多出一个无主的孤立环境，且发布的小程序与云端账号不对应，后续计费和审核全乱。

### 2.2 修正云凭证指向（最易踩坑、最隐蔽）

- **现象**：原 `utils/cloud-config.js` 的 `publishableKey` 前缀是 `Q0BvUcC34QxiYVHs0aFeay`
  （**旧应用**），与当前应用 `wbapp_XuxCaYOHVeBjdrJ4UfSMX6` 不一致。
- **改法**：把 `resourceId` / `endpoint` / `publishableKey` 全部换成新 app 的 `publicConfig`
  （`resourceId=wbcs_lyWv0kj2M9PBotd3mDopm9`，网关 `https://mp-api.app.workbuddy.host`，新 `publishableKey`）。
- **必要性**：
  - `publishableKey` 的作用是**标识「是哪个应用」**，服务端按来源校验。
    指错应用 → LLM 调用落到旧账号 / 旧环境，点评要么失败，要么扣错额度，且报错信息不一定直白。
  - **关键隐性回归点**：每次「重建 / 重新发布应用」之后，代码仓库里的云配置**不会自动跟着变**。
    它仍停留在上次构建时写入的旧 `publicConfig`。所以「重新构建并发布」之后，第一件该查的事就是
    「云凭证指向的 appId 是不是当前这个应用」。

### 2.3 隐私清单（合规必须）

- **动作**：写入 `.wbapp_XuxCaYOHVeBjdrJ4UfSMX6.privacy.json`，声明 `Clipboard`。
- **必要性**：代码里 `utils/device.js#copyText` 调用了 `wx.setClipboardData`（复制 FEN / 点评文字）。
  微信审核要求任何隐私接口都必须事先在隐私清单里声明，漏了会导致**审核被拒**或运行时受限。
- 排查方法：全仓库 grep `wx.` 的隐私接口（定位/相册/剪贴板/蓝牙等），只用到的才声明，避免冗余。

### 2.4 真实网络探针验证（关键，不能省）

- **动作**：临时写 `_probe_tmp.js`，用新凭证直接打真实云端：
  - `cloud.llm.models.list()` → 返回 **31 个可用模型**（`MODELS_OK total=31 usable=31`）；
  - `cloud.llm.chat.completions.create({ stream:true })` → `deepseek-v4-flash` 正常流式返回点评文本。
  - 验证完**立即删除**探针，不留在仓库。
- **必要性**：
  - 单元测试（cloud-adapter）只 mock 配置，证明的是「适配器逻辑对」，**不是**「真实数据面通」。
  - 「测试全绿」≠「云可用」。只有真实调用能同时确认：凭证路由正确、网关可达、账号额度正常。
  - 因此「重跑回归测试」与「真实探针」是**两件互补的事**，缺一不可：
    前者防止代码回归，后者证明环境真能用。

### 2.5 回归测试门禁

- **动作**：改完 `cloud-config.js` 后重跑 `cloud-adapter` 测试，结果 **68/68 全绿**。
- **必要性**：配置变更可能破坏适配器层；按项目约定，每次发布前必须跑全套 4 套回归
  （`engine-and-game` 153 / `cloud-adapter` 68 / `analyze-page` 185 / `agent-tools` 48，共 454 项）。

## 4. 可复用经验（落为团队惯例）

1. **重建 / 重发应用后，第一件事核对云凭证**：`utils/cloud-config.js` 的 `publishableKey`
   前缀必须 == 当前 `applicationId`；不一致就是指向旧应用的隐蔽回归。
2. **云服务接入 = 4 步闭环**：开通（reuse）→ 改凭证指向 → 隐私清单 → 真实探针。
   任何一步省略都会导致「看着正常、实际不通」。
3. **「测试全绿」只覆盖逻辑，「真实调用」才覆盖数据面**：临时探针用完即删，别留存仓库。
4. **隐私清单按需声明**：先 grep 仓库用到哪些 `wx.` 隐私接口，再最小集合声明，避免审核问题。
5. **凭证只放 publicConfig**：`endpoint` + `publishableKey` 可随前端发布；长期密钥 / 环境 id / 服务端凭据**绝不**进前端。
