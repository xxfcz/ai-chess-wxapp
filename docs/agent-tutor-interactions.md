## 0. 这份文档要解决的三个问题

1. **增量失控**：阶段一宣称「零新增控件」、阶段二要加追问、阶段三要加记忆档案。三次各自往下堆控件，界面会崩。
2. **口径不一致**：同一个"超时"，阶段一显示"请求超时"，阶段二显示"生成未完成，请重试"。这在真机上是信任杀手。
3. **误判产品形态**：很容易顺手做成一个聊天机器人。**那是最坏的方向**——理由见 §1.1。

> 本篇只冻结**交互契约与文案口径**，不写实现清单。三个阶段具体怎么落地，以各自的阶段文档为准。

## 1. 交互第一性原则

六条，按不可妥协程度排序。后续任何交互设计都要先过这六条。

### 1.1 Tutor 必须能「指」棋盘，否则它只是个会说话的文本区

这是本产品与普通 LLM 应用唯一的、也是最深的差异。

用户读完「白方应该走 Nf3，控制中心并为王翼易位做准备」之后真正想知道的是：**Nf3 是哪个子、走到哪一格、然后局面长什么样**。  
如果一个 Chat UI 只能输出文字，它不如直接去用通用大模型。

因此一条硬要求：**Tutor 输出的每一条结论，都要能落到棋盘上的一个具体对象**（走法 / 格子 / 棋子 / 一条完整的演示线）。  
现有的三类富文本记号（`move` / `sq` / `piece`）与紫色 `focus` 高亮已经做到了这件事，**这是资产，不是历史包袱**。

### 1.2 棋盘主权不可侵犯

- 棋盘是屏幕上**唯一不滚动**的元素，固定在半屏（AGENTS.md §3）。任何 Tutor 控件不得以任何理由挤压、遮挡、覆盖它。
- 只有**演示态**可以接管棋盘，且必须同时满足：跑在临时副本上（不污染真实棋局）、真实棋盘操作提前 return、`退出演示` 一键可回。
- 演示期始终有一条面包屑告诉用户「这不是你的真实棋局」(现有 `view().breadcrumb`)。

### 1.3 过程可见，但原始过程不可见

用户需要知道"它没卡住"，但不需要知道"它调用了 `compare_moves` 并返回了一个 cpDiff 数组"。

- ✅ 可见：`正在验算第 2 步：黑方最顽强的应对…`
- ❌ 不可见：JSON、工具名、FEN 串、节点数、token 数

原始调用明细属于「运行日志」Tab 的职责，两条通道都保留，互不污染。

### 1.4 宁慢勿错，所以 UI 必须能优雅地承载长时间等待

阶段二已经定了产品判断：**错误的「为什么」比没有回答更有害**（棋手会记住错误的因果）。  
代价是单次应答可能到 15~30s。

因此 UI 的义务是：**让 30s 的等待不像卡死**（§5.4 给出具体做法）。反过来，UI 不得为了让数字好看而引入虚假进度（见 §5.4 的禁忌）。

### 1.5 任何时刻可中断，中断后零请求

用户按取消之后，**不得再产生任何网络请求**（含重试）。这条是红线，阶段二 R5 已定，交互侧的等价要求是：

- 取消按钮必须在等待期**始终可见且可点**；
- 取消后 UI 立即回到可用态，不留旋转菊花；
- **中断不能以错误态呈现**（"生成失败"会让用户以为是系统问题）。保留已生成的部分正文。

### 1.6 失败必须可归因，不许甩锅也不许含糊

- ❌ 禁用：`服务繁忙，请稍后再试`（零信息量）、`AI 出错了`（既甩锅又无信息）、`生成失败`（不说是谁的问题）
- ✅ 要求：说清是**网络 / 超时 / 模型 / 额度 / 无此能力 / 用户取消**中的哪一类，并给一个**用户此刻能做的动作**。

现有 `describeLLMError()` / `llmErrorInfo()` 已经在做归因，§8 把它的输出统一成文案表。

### 1.7 教学姿态不止一种：讲 / 演 / 问 / 练

容易被忽略的一点：**同样一句正确的建议，用不同姿态说出来的教学效果差别很大。** Tutor 至少要支持四种：

| 姿态    | 是什么                       | 现状 / 何时可用               |
| ----- | ------------------------- | ----------------------- |
| **讲** | 直接给结论 + 理由                | 现状唯一有的姿态                |
| **演** | 把结论变成盘上可逐步回放的一条线          | 有，但阶段一之后才可靠（如今演示线会断）    |
| **问** | 不吐答案只给线索：「数数黑方有几个子在打 e4？」 | **当前完全没有**；阶段二具备验算能力后可做 |
| **练** | 针对已知弱项主动喂招，事后复盘           | 阶段三（依赖棋力画像）             |

**「问」是差异化最大的一档，也是最容易被漏掉的一档。** 棋力靠自己算出来才长在身上，直接给答案反而削弱训练效果；  
而市面上的 AI 棋类产品默认姿态清一色是「讲」——同质化最严重的地方，恰恰最值得做。

设计约束：`问` 必须是**可退让的**——用户连着没答上来、或直接说「告诉我吧」，就得立刻切成 `讲`。  
把提问当成目的的产品会让人烦躁，把它当成可选的练习模式才成立。

> 顺带定性阶段价值：**关于局面的六个讲解维度里五个都卡在同一处**——都需要「沿某条线走下去看会发生什么」。  
> 所以阶段一是把现有能力做可靠，阶段二才真正带来新能力；`问` 姿态也顺势在此解冻。

## 2. 现状：界面基线

改动要落在真实的东西上。当前「AI教练点评」Tab 的实际元素（`analyze.wxml` 第 115~156 行）：

| 元素          | 状态字段                                                                                             | 说明                            |
| ----------- | ------------------------------------------------------------------------------------------------ | ----------------------------- |
| 标题          | ——                                                                                               | 「AI 教练点评」                     |
| 生成点评 / 取消生成 | `commenting`                                                                                     | 同一个按钮双语义：生成中=取消。**这个设计很好，保留** |
| 复制          | `coachText \|\| demoLines.length`                                                                | 卡片头常驻按钮（照顾预览环境不支持长按）          |
| 等待提示        | `commentingHint`                                                                                 | 由 1s 定时器更新                    |
| 正文富文本       | `coachSegments`                                                                                  | 三类记号可点                        |
| 错误 / 详情     | `coachError` / `coachDetail`                                                                     | 详情是技术行，不主打给用户                 |
| 模型归属        | `coachModel`                                                                                     | 「本条点评由云端模型 X 生成。」             |
| 演示线区        | `demoLines` / `demoActive` / `demoBreadcrumb` / `demoPlaying` / `demoCanBack` / `demoCanForward` | 面包屑 + 上一步/下一步/播放/退出 + 分支列表    |

### 2.1 现有病灶（交互层面）

| #  | 现象                                                     | 根因                                                                                   | 在哪一阶段解决  |
| -- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ | -------- |
| I1 | 演示线时有时无、偶尔只有 1 手，正文里对应的走法链接点不动                         | 让 LLM 拼写 SAN                                                                         | 阶段一      |
| I2 | 等待期只有一个静态提示，5s 之后用户普遍以为挂了                              | 无从表达过程                                                                               | 阶段二      |
| I3 | 看完点评想追问「为什么不能走另一手」，**没有入口**                            | 单次往返设计                                                                               | 阶段二      |
| I4 | 演示线的控制按钮大概率失效                                          | `DemoSession.view()` 返回 `active/canBack/...`，模板读 `demoActive/demoCanBack/...`，字段名不一致 | 阶段一（顺手修） |
| I5 | 每次点评都像第一次见面                                            | 无记忆                                                                                  | 阶段三      |
| I6 | 流式期间每个分片都 `setData` 全文，且每片跑一次 `stripDemoBlock` → O(n²) | 未节流                                                                                  | 阶段一（顺手修） |

> I6 是当前唯一已知的**性能型**交互缺陷：768 token 的输出按 SSE 分片可能有几十到上百次回调，  
> 每次都把累积全文推给视图层。建议在 `onDelta` 里做 ≥120ms 节流；`stripDemoBlock` 只对最后一个分片必须算。

## 3. 交互地图：三个阶段的界面增量

| 阶段                      | 新增交互                         | 是否动棋盘   | 是否新增 Tab | 影响既有布局  |
| ----------------------- | ---------------------------- | ------- | -------- | ------- |
| 一 · Candidate Grounding | **无新增控件**（见 §4）              | ✅ 演示态不变 | 否        | 无       |
| 二 · Reason-Act Loop     | 追问输入框 + 对话卡片流 + 过程状态行 + 快捷提问 | ✅ 演示态不变 | 否        | 本 Tab 内 |

## 4. 阶段一交互：除了更稳，什么都不变

这条要与 `agent-phase1-tutor.md` §3.1 保持一致：**用户感知到的唯一变化是「演示线不再莫名其妙断掉」**。

具体到交互契约，只有三条可以对外承诺：

| #  | 承诺                     | 用户怎么说            |
| -- | ---------------------- | ---------------- |
| C1 | 演示线里的每一手都点得动           | 「点走法一定有反应」       |
| C2 | 每条演示线的第一手一定是当前局面下的合法走法 | 「推荐的棋，第一步不可能走不了」 |
| C3 | 对比线（bad tone）稳定出现      | 「它会不会告诉我哪手不能走」   |

### 4.1 唯一可选的微小增强

在现有「本条点评由云端模型 X 生成。」那一行，**追加来源信息**：

```
本条点评由云端模型 deepseek-v4-flash 生成，走法由本地引擎校验。
```

成本一行字，收益是**把「这次不是模型瞎编的」明示给用户**——本产品原本最大的病灶正是模型幻觉，这句值得写。  
若担心小屏换行，可降为 `走法已由本地引擎校验`。

### 4.2 演示线的字段名对齐：`DemoSession.view()`

I4 是已知的字段名不一致，阶段一开工会动 `coach-demo.js`，届时顺手统一。  
**方向统一到模板一侧**（`view()` 返回 `demoActive/demoBreadcrumb/...`），理由是字段名改动在 WXML 侧扩散更广、更容易漏。  
现有的回归断言已经把「双方字段名不一致」的现状钉住，改名时它们会红——这是故意的。

## 5. 阶段二交互：追问（本节是全篇最大的界面变量）

### 5.1 明确否决的形态：不要做成聊天窗口

直觉做法是加一个气泡对话。**在这个产品里它是错的**，三个理由：

1. **挤压棋盘**（违反 §1.2）。气泡流越长，留给棋盘的空间越少——而棋盘恰恰是答案所在。
2. **与本页滚动架构冲突**。AGENTS.md §3 明确写着「状态/控制按钮与 Tab 内容同属一个 scroll-view 整体滑动，Tab 内部不再各自滚动」。  
   对话窗口天然需要**自己的独立滚动区**，这与此前的架构决策正面对撞。
3. **它有更好的做法**（下一节）。

### 5.2 采纳的形态：同一 Tab 内的「对话卡片流」

```
┌─ AI 教练点评 ─────────────────────────────┐
│ [生成点评] [复制]                            │
│                                            │
│ ▸ 第 1 轮 · 点评                             │
│   正文富文本（走法/格子/棋子可点）              │
│   演示线区（保持不变）                        │
│                                            │
│ ──────── 以上针对旧局面 ────────  （归档条）   │
│                                            │
│ ▸ 第 2 轮 · 追问「为什么不能 Nc3？」           │
│   正在验算第 2 步：黑方最顽强的应对…            │
│                                            │
├────────────────────────────────────────────┤
│ 快捷：[为什么推荐 #1？] [ #2 差在哪？] [还有更好   │
│        的吗？]                               │
│ ┌──────────────────────────┐ [发送]         │
│ │ 输入你想问的…              │               │
│ └──────────────────────────┘               │
└────────────────────────────────────────────┘
```

四条布局纪律：

1. **新内容追加在下方**，用 `scroll-view` 的 `scroll-into-view` 跟随（该能力是模板属性，不依赖缺失的 `createSelectorQuery`，预览可用）。
2. **只渲染最近 3 轮**，更早的折叠成「查看更早的对话」——无限增长的列表会拖垮 `setData`。
3. **输入框放在本 Tab 底部**而不是做吸底栏：吸底栏会和底部五个 Tab 打架，且键盘弹起时更乱。  
   用 `<textarea>` + `adjust-position` + `cursor-spacing`（经 `device.js` 探测降级）。
4. 每一轮卡片自带：`role` / `idx` / `key`（字符串）/ `kind`（点评 or 追问）/ `stale`（是否已随局面失效）。  
   ——这是 AGENTS.md §6.4 的硬约束（不得在 `wx:for` 元素自身属性里引用 `index`）。

### 5.3 快捷提问比输入框更重要

手机输入成本很高，而且**大多数用户根本不知道该问什么**。  
更进一步——**问句本身也可以由端上生成**，这与「确定性计算下沉」的总原则是一致的：

| 由端上生成的提问           | 依据                      |
| ------------------ | ----------------------- |
| 「为什么推荐 #1 而不是 #2？」 | 候选池里 top-2 分差很小，值得解释    |
| 「走 #4 会怎么样？」       | 候选池里明明的劣手，天然适合做反例       |
| 「这一步之后对方最好的应对是什么？」 | `expand_line` 已算好       |
| 「我这里是不是有威胁？」       | `describe` 发现对方王安全/悬子异常 |

动态生成 2~3 个 + 一个固定兜底（可以自由输入），**命中率会显著高于空白输入框**。建议把它列为本阶段的必做项而非锦上添花。

### 5.4 过程反馈的具体做法

| 要做                                                 | 不要做                                        |
| -------------------------------------------------- | ------------------------------------------ |
| **延迟 800ms** 后才显示过程态——低于此来的请求直接看到答案更好，频繁闪烁的过程行反而焦虑 | 一开始就显示「正在思考…」                              |
| 单行，随步骤更新：`正在验算第 2 步：黑方最顽强的应对…`                     | 把每一次工具调用都列出来（那是运行日志）                       |
| 超过 8s 才在行尾显示已用秒数（`已 12 秒`）                         | 用进度条——我们没有可靠的完成百分比，假进度是撒谎                  |
| 过程态用**单一字段**更新（如 `tutorStatus`）                    | 依赖 `setData` 路径语法做部分更新（AGENTS.md §6.4：不稳定） |
| 到达 30s 硬上限时，正常给出「我能确认到这一层」的答复                      | 抛「超时错误」——半截但有据的答案强于错误页                     |

### 5.5 中断、改主意、预算耗尽

| 场景              | 交互表现                                                            |
| --------------- | --------------------------------------------------------------- |
| 用户按「取消生成」       | 立即回可用态；**保留已生成的部分正文**；不以错误态呈现（`coachError` 留空）                  |
| 走了一步新棋 = 会话锚定失效 | 旧轮次**不删除**，整体降透明度 + 插入一条「以上针对旧局面」分隔条；旧轮的演示线不再可点（否则会在真实棋盘上演示错局面） |
| 预算耗尽（轮次/调用数/墙钟） | 答复正常出现，卡片顶部一行小字：`本次对话的计算预算已用尽，可以换个角度继续追问。`                      |
| LLM 单步失败换模型重试   | **不打扰用户**；仅在该轮最终成功且换了模型时，在元信息行体现                                |

> 「取消」按钮当前已有双语义（生成中=取消），这个设计保留即可，不要为了「看起来严谨」把它改成需要二次确认。

### 5.6 可回溯：让结论指向依据

每条答复下方一个折叠的「查看依据」，展开后列出该轮用到的**已压缩、人类可读**的步骤：

```
▸ 查看依据
  · 比较了 Nc3 与 Nd2（各 6 层）
  · Nc3 后被 Qb6 打双，落后约 1.2 兵
  · Nd2 保持结构完整
```

这不是装饰：**可回溯性是用户信任「它不是在编」的唯一凭据**。阶段二 R9 已要求工具结果必须压缩，此处的展示形态应与之一致。

## 6. 阶段三交互：记忆必须可见、可纠、可清

### 6.1 入口与形态

不放新 Tab（§3），在「AI教练点评」卡片头部放一个小入口 `我的教练档案`，进入后在本 Tab 内替换内容，提供返回。

档案至少包含：

- **错误分布图**（总纲 §2.1 ① 的形态）。这条单独成立——大多数棋手从没见过自己的错误分布，光这张图就是价值。
- **错题本**：按失败模式聚合，每条显示「首次 / 最近 / 次数 / 是否还在犯」。**必须显示 `resolution`（改善中）**，否则用户会觉得被反复翻旧账。
- **话题主线**：本局已讲/未讲，用户能看到"还有什么没聊到"。

### 6.2 三条容易被漏掉、但很关键的交互

1. **允许用户对标签纠错**（「这条不对」）。  
   画像是从行为推断的，错误难免。**没有纠错通道的错误标签会一直错下去**，且用户无从申诉。这条应作为隐私原则之外的第四条硬要求。
2. **主动提及要有频控**。  
   同一局同一类错误**最多提示一次**；语气是「这里我们上次也漏过 f7 的威胁」而非「你又犯了」。否则教练会变成事后诸葛亮。
3. **首次使用时用一句话说明存了什么、没存什么**。  
   不要长隐私政策。一句话 `: 只记录你的棋类错误分布用于讲解，随时可清除。` 加一个可点开看的明细就够了。

### 6.3 记忆对其他交互的影响

| 影响点     | 表现                                                |
| ------- | ------------------------------------------------- |
| 讲解深度自适应 | 残局弱的用户，演示线的 `extend` 手数自动 +1~2（仍受「每条不超过 6 手」上限约束） |
| 快捷提问    | 生成的问题优先覆盖用户的高频错误维度                                |
| 首次生成点评  | 开场可简短承接上次话题，但**不得超过 1 句**；用户是来看这一局的，不是来续旧         |

## 7. 状态机：一次 Tutor 会话

```
                      ┌──────────┐
         生成/追问 ──▶ │ preparing│  候选预生成（端上，≤50ms，用户无感）
                      └────┬─────┘
                           ▼
                      ┌──────────┐
                      │streaming │  分片到达；≥120ms 节流后才 setData
                      └────┬─────┘  （此期间：可取消；暂不做富文本解析）
                ┌──────────┼──────────────┐
           完成 │          │ 阶段二未完成   │ 失败/取消
                ▼          ▼              ▼
        ┌───────────┐  ┌─────────┐  ┌──────────┐
        │ grounding │  │verifying│  │ failed / │
        │ 生成演示线 │  │ 验算循环 │  │ aborted  │
        └─────┬─────┘  └────┬────┘  └──────────┘
              │             │ 超预算 → summarizing（用已得结果总结）
              ▼             ▼
        ┌────────────────────────┐
        │ ready                  │  富文本 + 演示线就绪；可追问
        └───────────┬────────────┘
                    │ 用户走了新的一步
                    ▼
        ┌────────────────────────┐
        │ stale                  │  旧内容保留 + 归档条；再问即开新会话
        └────────────────────────┘
```

对 UI 的约束一句话：**这些状态对用户只需三种可见形态**（等待中 / 有内容 / 有内容但已过期），  
内部再多也不可以外溢成 UI 复杂度。`aborted` 尤其不能显示为失败态。

## 8. 文案口径统一表

阶段一二三共用一份。所有错误文案**必须**来自 `describeLLMError()` / `llmErrorInfo()` 的归因结果，禁止各处手写。

| kind             | 用户可见文案（主）                 | 建议动作             | 可重试     |
| ---------------- | ------------------------- | ---------------- | ------- |
| `network`        | 网络不通，无法连接点评服务。            | 检查网络后重试          | ✅ 手动    |
| `timeout`        | 这次点评用时过长（超过 30 秒），没有拿到结果。 | 重试；仍失败可换个局面或稍后再试 | ✅ 手动    |
| `model`          | 点评模型暂时不可用。                | 已自动换用其他模型重试一次    | ⚠️ 自动一次 |
| `auth` / `quota` | 点评额度已用完或服务未开通。            | 更换/开通服务后重试       | ❌       |


| `param` | 请求参数有误。 | 换局面重试；持续出现请反馈 | ❌ |
| `env_no_network` | 当前环境不支持网络请求，云端点评不可用。 | 端上引擎分析不受影响，可继续使用 | ❌ |
| 用户取消 | **不显示错误**，保留已生成的部分正文 | —— | —— |
| 预算耗尽 | 本次对话的计算预算已用尽，答复可能不完整。 | 换个角度继续追问 | ✅ 新追进 |

两条硬规矩：

1. **技术细节进 `coachDetail`，不进主文案**。主文案面向"我现在该怎么办"，技术行面向"我要排查"。
2. **同一 kind 全项目同一句**。改文案改这张表，不要在页面里逐处改。

改交互前重读这些，它们是**结构性限制**，不是偏好：

| 约束 | 出处 | 对交互设计的直接影响 |

| 棋盘不用 Canvas，用 view 网格 | AGENTS.md §6.1 | 棋盘可视化只能用 inset box-shadow 叠色；不要设计渐变/箭头的棋盘标注 |

## 10. 验收口径

每条第一性原则对应一个可走查的场景，对错在人，不在测试：

| 原则 | 验收场景 |
|---|---|
| §1.1 能指棋盘 | 随机取 5 条点评，每条挑一个正文里的走法点击 → 棋盘必须走到对应手且正确高亮；**100% 命中，无一次"点了没反应"** |
| §1.2 棋盘主权 | 从开启点评到演示、追问、取消、查看档案的全过程，棋盘始终可见且未被遮挡/挤压 |
| §1.3 过程可见 | 追进过程中，界面至少有 **1 次**中间态更新；且界面上**不出现**任何 JSON / FEN / 工具名 |
| §1.4 承载长等待 | 人为延迟到 25s：过程态正常更新、不闪烁、可取消；到 30s 强制出答复而非报错 |
| §1.5 中断零请求 | 取消后抓 10s 网络包：新请求数 = 0；界面不得显示为失败 |
| §1.6 可归因 | 逐个注入 network/timeout/model/quota/env_no_network，界面文案与 §8 表格一字不差 |

补充性能红线：

- 追进从发送到**首个可见字符** 建议 ≤ 3s（不含工具验算）
- 流式期间 `setData` 频率 ≤ 8 次/秒（当前是每片一次，需节流）
- 演示线构建发生在解析阶段，**不得**阻塞任何一帧的输入
